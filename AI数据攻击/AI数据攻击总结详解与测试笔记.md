# AI 数据攻击（AI Data Attacks）总结、详解与测试笔记

> 适用范围：AI/ML 数据安全学习、架构威胁建模、授权红队测试和上线前审计。本文只讨论风险识别、防御和无害验证。测试必须使用合成数据、隔离环境、低权限账户和可恢复的模型副本；不得向真实训练集、生产反馈回路或临床、金融等高影响系统注入测试数据。

> 前置知识：[[AI数据管线与攻击面]]。上一节描述数据从收集到再训练的正常流向，本节分析攻击者如何蓄意破坏这条管线。

## 使用方式：数据攻击快速审计入口

```text
先定攻击面 → 建干净基线 → 构造最小授权污染
→ 公平重训 → 分组评估 → 检测与消融 → 修复复测
```

开始前：

```text
[ ] 明确攻击发生在收集、标注、特征、训练、模型还是反馈阶段
[ ] 明确攻击者能改 X、y、metadata、pipeline、weights 中的哪些对象
[ ] 使用隔离副本、合成数据和可恢复模型
[ ] 固定数据划分、模型、超参数、seed 和评估集
[ ] 保存数据版本、样本 ID、来源、标签与文件哈希
```

最少报告：

```text
干净基线 vs 污染模型
总体指标 + 逐类/逐群体指标
攻击预算（数量、比例、扰动）
目标成功率与自然误判率
多随机种子、检测与消融结果
修复后的完整回归结果
```

快速判据：

```text
总体 Accuracy 高 ≠ 没有定向攻击
标签未变 ≠ 数据干净
磁盘文件未变 ≠ 动态数据管线未投毒
一次成功 ≠ 可复现
删除异常点后恢复 ≠ 已充分证明因果
```

## 0. 一页速记

### 0.1 定义

AI 数据攻击是指攻击者故意破坏模型所学习的数据、生成数据的处理逻辑，或模型的存储与交付形式，使模型学习错误关系、产生攻击者指定行为，甚至在加载模型文件时危及运行基础设施。

```text
恶意数据 / 被篡改的处理代码 / 被替换的模型文件
    ↓
进入收集、存储、处理、训练、部署或再训练阶段
    ↓
正常自动化流程继续信任并传播污染
    ↓
偏置与错误预测 / 隐藏后门 / 模型完全失陷 / 代码执行
```

其关键特征是：当生产系统开始预测时，损害通常已经被写入数据、模型行为或模型文件。

### 0.2 与规避攻击、隐私攻击的区别

| 攻击族 | 主要时机 | 主要目标 | 典型结果 |
|---|---|---|---|
| 数据攻击 | 训练前、训练中、模型交付或再训练时 | 训练数据、处理逻辑、模型产物 | 模型学错、后门、模型替换或代码执行 |
| 规避攻击（Evasion） | 推理时 | 单次或一批生产输入 | 已部署模型被特制输入欺骗 |
| 隐私攻击（Privacy） | 通常在模型可查询或可访问时 | 模型记忆、训练成员和敏感属性 | 提取或推断敏感训练信息 |

一句话区分：

```text
数据攻击：提前改变模型学到了什么或加载了什么。
规避攻击：推理时改变模型看到了什么。
隐私攻击：从模型中反推出它记住了什么。
```

### 0.3 六个管线阶段与对应攻击

| 管线阶段 | 主要攻击方式 | 直接对象 | 主要影响 |
|---|---|---|---|
| 数据收集 | 数据投毒 | 用户输入、评论、日志、传感器、临床记录 | 恶意样本进入训练集 |
| 存储 | 数据篡改、模型替换、恶意模型文件 | 数据湖、文件系统、模型仓库 | 绕过接入验证、植入木马或代码载荷 |
| 数据处理 | 处理逻辑操纵 | 清洗、标签、归一化、特征工程代码 | 干净原始数据被转换为污染数据 |
| 分析与建模 | 吸收上游污染 | 训练作业、验证过程 | 错误模式、偏置和后门固化为模型能力 |
| 部署 | 模型交付路径注入 | CI/CD、模型拉取端点、传输链路 | 未经批准的模型进入生产 |
| 监控与维护 | 在线投毒、再训练利用 | 点击、评分、反馈、新数据 | 污染跨版本缓慢累积 |

### 0.4 三种后果必须分开

| 后果 | 被破坏的安全属性 | 表现 |
|---|---|---|
| 预测完整性受损 | 模型行为 | 准确率下降、系统性偏置、攻击者指定分类 |
| 隐藏后门 | 条件性模型行为 | 干净输入表现正常，特定触发输入激活恶意输出 |
| 基础设施失陷 | 模型文件加载边界 | 反序列化触发代码，危及服务账户、主机或网络 |

> “模型被投毒”和“加载模型文件导致代码执行”不是同一个问题。前者影响模型学到的行为，后者利用文件格式或加载器危及执行环境。

## 1. 总体攻击面

### 1.1 攻击目标

攻击者可能追求：

- 降低整体预测质量；
- 让特定商品、账户、诊断或类别得到偏向结果；
- 对某一群体形成系统性偏置；
- 植入仅在特定触发条件下生效的后门；
- 用恶意模型文件获得代码执行；
- 通过模型服务账户继续访问存储、凭据或内部网络。

### 1.2 为什么攻击不一定表现为系统故障

最危险的数据攻击往往保持管线“正常运行”：

- 数据格式合法；
- API 返回成功；
- ETL 作业按时结束；
- 训练损失正常下降；
- 总体准确率仍然可接受；
- 部署健康检查全部通过。

攻击破坏的是数据含义、统计关系、特定条件下的模型行为或产物完整性，而不是一定让程序崩溃。

### 1.3 攻击面与控制面

```text
数据面：样本、标签、特征、反馈、模型权重
代码面：采集器、清洗脚本、特征工程、训练与加载代码
交付面：对象存储、模型注册表、CI/CD、拉取端点、网络链路
身份面：用户、数据供应商、服务账户、维护人员、训练与部署角色
```

只保护数据文件而忽略代码、身份或交付链路，无法形成完整防线。

## 2. 数据收集阶段：数据投毒

### 2.1 入口机制

攻击者不一定需要入侵系统。他们可以使用系统原本就开放并信任的输入渠道提交恶意数据，例如：

- 商品评论、点击、评分和购买行为；
- 用户纠错或人工反馈入口；
- IoT 设备读数；
- 第三方批量数据；
- 图像、文本和元数据上传；
- 临床笔记、诊断代码或影像元数据录入路径。

攻击数据拥有正确格式并通过正常 API，不代表其语义、标签和意图可信。

### 2.2 标签翻转（Label Flipping）

标签翻转是指让样本和它应有的类别发生错误对应。

```text
原始含义：恶性样本 → 标签“恶性”
被操纵后：恶性样本 → 标签“良性”
```

翻转可以发生在：

- 用户提交数据时；
- 数据库存储后；
- 标注人员或标注平台中；
- 处理脚本生成派生标签时；
- 反馈被自动转换为训练标签时。

因此，看到训练表中的错误标签并不能直接判断攻击入口。

### 2.3 特征攻击（Feature Attacks）

特征攻击操纵样本携带的输入值，同时可能保留表面上合理的标签。

例子包括：

- 调整图像像素或元数据；
- 在评论中加入特定关键词模式；
- 修改数值特征或时间字段；
- 操纵临床文本中被特征提取器重点使用的词语；
- 制造大量看似自然但统计分布经过设计的交互。

单个改动可能很小，但重复进入训练集后会改变模型学习到的关系。

### 2.4 后门触发器

后门攻击让模型在普通输入上维持正常表现，只在输入含有特定模式时产生攻击者指定结果。

```text
正常输入              → 正常预测
带特定关键词/图案输入 → 攻击者指定预测
```

触发器可能是关键词组合、像素图案、元数据字段或某种特征关系。真正危险之处在于常规验证集若不包含触发条件，模型仍可能顺利通过验收。

### 2.5 电商实例

攻击者为目标商品提交大量虚假好评：

```text
正常评论 API
  ↓
格式合法的虚假评论和评分
  ↓
评论情感与用户偏好特征
  ↓
推荐模型训练
  ↓
目标商品排序被人为抬高
```

部分评论还可能反复包含特殊关键词，使这些模式成为潜在后门触发器。

### 2.6 医疗实例

具有数据接入路径权限的攻击者可能：

- 修改 DICOM 元数据；
- 对图像特征做微小扰动；
- 交换临床笔记中的诊断代码；
- 重复提交带有相同偏差的样本。

当足够多的污染样本进入训练集，模型可能产生错误分类、系统性偏差或条件触发行为。医疗场景影响患者照护，必须采用更严格的来源验证和人工复核。

### 2.7 检测重点

- 单一来源的数据量或贡献比例异常；
- 重复、近重复和协同行为；
- 标签与独立证据不一致；
- 特征或标签的时间分布突变；
- 某些稀有词、图案或元数据与目标类别异常强相关；
- 总体指标稳定，但特定商品、类别或群体突然偏移。

## 3. 存储阶段：数据篡改与模型文件攻击

### 3.1 存储层的两类攻击

#### 第一类：篡改数据集

攻击者获得 AWS S3、共享文件系统、数据库或医疗安全存储的未授权写权限后，可以：

- 修改标签；
- 替换样本；
- 扰动已存储特征；
- 删除能抵消偏差的数据；
- 修改训练、验证或测试集之间的划分。

这种攻击绕过采集入口的验证，是从另一个入口完成数据投毒。

#### 第二类：攻击模型文件

模型文件本身是高价值产物。攻击者可以：

- 用带后门的模型替换合法模型；
- 修改权重，使特定输入产生目标输出；
- 在具备危险反序列化语义的文件中嵌入代码载荷；
- 篡改模型元数据，使部署系统选择错误版本。

### 3.2 模型木马（Trojaned Model）

模型木马通常强调行为层后门：

```text
干净输入 → 表现正常，用于逃过常规评估
触发输入 → 输出攻击者预设结果
```

木马可以通过投毒训练获得，也可以由攻击者直接提供或替换模型产物。

### 3.3 模型文件中的隐藏代码

攻击者还可能把代码或其他载荷隐藏在模型文件中。需要精确区分两个概念：

- 隐写/隐藏（Steganography）：把载荷隐藏在模型权重、冗余空间或文件结构中；
- 危险反序列化：加载器在恢复对象时执行文件指定的构造逻辑。

隐藏载荷本身不会必然执行；要形成代码执行，必须存在会解释或执行它的加载路径。

### 3.4 Pickle 风险

Python pickle 不是安全的纯数据格式。对不可信文件调用 `pickle.load()` 可能在反序列化期间执行文件内指定的 Python 调用。

```text
攻击者可写模型文件
    +
应用未经验证地加载 pickle
    +
模型服务账户拥有文件、网络或云权限
    =
服务基础设施可能被接管
```

`.pkl` 扩展名不是判断依据，改名也不会消除风险。某些框架格式和加载 API 在特定版本、参数或保存方式下也可能依赖 pickle，因此审计时必须核实实际框架版本、保存格式和加载参数，不能只根据 `.pt`、`.pth` 等扩展名下结论。

### 3.5 影响扩展

- 推荐模型在 Flask API 中加载恶意文件，可能危及 API 主机或容器；
- 临床系统加载恶意模型，可能让攻击从模型服务扩展到内部网络；
- 被盗的服务凭据可能进一步访问数据湖、模型仓库或其他云资源。

代码执行的严重性取决于加载服务的权限和网络可达范围，因此模型服务必须遵循最小权限和隔离原则。

### 3.6 检测与控制重点

- 模型和数据对象启用不可变版本与审计日志；
- 对批准产物记录哈希和签名；
- 分离训练写权限与生产读取权限；
- 生产仅从受控模型注册表拉取已批准版本；
- 禁止加载来源不明的 pickle 或模型文件；
- 在隔离、无凭据、低权限环境中检查第三方模型；
- 对对象覆盖、异常写入和权限变更告警。

## 4. 数据处理阶段：处理逻辑操纵

### 4.1 攻击对象不是原始数据

处理阶段攻击针对：

- 清洗脚本；
- 标签生成规则；
- 数值缩放与归一化；
- 图像标准化与增强；
- 文本特征提取；
- Spark 作业配置；
- Airflow DAG 或其他编排定义。

原始数据仍可通过完整性检查，但处理输出已经被污染。

### 4.2 电商实例：篡改情感分析

攻击者修改 Spark 作业，使情感标签发生反转：

```text
原始正面评论 ─┐
              ├→ 被篡改的情感作业 → 负面标签
原始负面评论 ─┘                    → 正面标签
```

这同样是标签翻转，但攻击点是处理代码，不是原始评论。

### 4.3 医疗实例：篡改标准化和特征提取

攻击者修改 Python 处理脚本，造成：

- 像素归一化发生轻微偏移；
- 特定设备或患者群体的图像被不同处理；
- 临床笔记提取出错误实体或否定关系；
- 某些诊断词被系统性忽略或错误映射。

模型最终学习的是被篡改的处理结果，而不是存储中的原始图像和笔记。

### 4.4 为什么更难发现

- 原始数据哈希没有变化；
- 接入验证仍然成功；
- 作业可能正常完成且没有报错；
- 错误被批量、稳定地施加到许多样本；
- 调查若只回看原始数据，会错过真正入口。

### 4.5 检测与控制重点

- 处理代码、配置和 DAG 必须进入版本控制；
- 生产运行只允许经过审查和签名的版本；
- 记录输入数据、代码提交、参数、依赖和输出哈希；
- 为关键转换建立固定样本的单元测试与黄金输出；
- 比较处理前后样本数量、标签和特征分布；
- 对未经批准的作业变更、临时 Notebook 和运行时注入告警。

## 5. 分析与建模阶段：上游损害固化

### 5.1 攻击面主要是继承而来

在本节的威胁模型中，建模阶段通常不是污染首次发生的位置。SageMaker 训练作业不会知道 Parquet 文件中的标签已被反转；PyTorch 训练循环也不会知道图像特征含有后门触发器。

```text
被污染的数据
  ↓
正常训练过程
  ↓
训练成功、损失下降
  ↓
错误关系、偏置或后门被固化到模型中
```

### 5.2 可能表现

- 整体预测性能下降；
- 特定类别持续被错误分类；
- 某些群体得到系统性不利结果；
- 模型在触发输入上产生攻击者指定输出；
- 平均指标正常，但尾部或少数群体性能异常。

### 5.3 验证为什么可能失效

- 验证集来自同一被污染管线；
- 训练集和验证集共享重复或近重复样本；
- 评估只看总体准确率；
- 没有后门触发测试；
- 未按来源、时间、群体和类别切分指标；
- 攻击影响逐版本累积，单次变化低于阈值。

### 5.4 检测与控制重点

- 使用来源独立、访问受控的验证与测试集；
- 检查总体指标和分群指标；
- 对稀有模式、异常高关联特征和可疑触发器做专项测试；
- 将新模型与最后已知安全模型比较；
- 记录并验证数据版本、代码版本、参数和模型哈希；
- 让批准流程检查证据链，而不仅是一个最终分数。

## 6. 部署阶段：模型交付路径注入

### 6.1 攻击位置

即使存储中的模型是安全的，攻击者仍可能在模型从存储进入生产环境的途中替换它：

- 配置错误的 CI/CD 管线；
- 缺少认证的模型拉取端点；
- 可被修改的部署清单或镜像；
- 不安全的共享卷或临时目录；
- 未正确保护的传输链路；
- 服务发现、DNS 或代理配置被操纵。

攻击者不一定需要对 S3 或模型注册表拥有直接写权限，只需要控制交付路径中的一个环节。

### 6.2 完整攻击链

```text
合法模型已通过验证
  ↓
部署任务开始拉取模型
  ↓
交付路径中的攻击者替换文件
  ↓
部署系统未校验哈希/签名/来源
  ↓
生产加载恶意模型
  ↓
模型后门或反序列化代码执行
```

### 6.3 关于中间人条件的精确判断

仅“处于网络路径中”并不自动代表能够替换模型。如果传输使用正确验证的 TLS，且部署端还验证产物签名或固定哈希，中间人应难以注入有效产物。风险来自认证、加密、证书验证、重定向处理或产物完整性校验中的缺口。

### 6.4 检测与控制重点

- 部署清单固定模型版本和哈希；
- 同时验证传输身份与产物签名；
- CI/CD 使用短期、最小权限凭据；
- 禁止从任意 URL 或未认证端点拉取模型；
- 构建和部署日志记录产物来源、摘要和批准状态；
- 生产启动时重新验证，而不是只在训练结束时验证；
- 发现不匹配时安全停止，不能自动降级到未验证文件。

## 7. 监控与维护阶段：在线投毒

### 7.1 为什么再训练是高价值入口

再训练管线被设计为吸收新数据。攻击者可以通过正常用户渠道提交：

- 被操纵的点击流；
- 误导性评分和反馈；
- 重复交互；
- 经过设计的查询与选择行为；
- 逐步影响未来标签的反馈。

这些输入会在多个再训练周期中积累，不需要直接入侵存储或处理代码。

### 7.2 渐进式污染

```text
周期 1：少量偏置，指标变化很小
周期 2：相同方向继续积累
周期 3：目标类别排序开始偏移
周期 N：模型行为明显被操纵，但单次版本差异仍不大
```

渐进式攻击的隐蔽性来自监控系统必须区分：

1. 真实用户行为发生分布漂移；
2. 正常随机噪声；
3. 攻击者主动制造的分布变化。

三者在统计外观上可能非常相似。

### 7.3 电商实例

攻击者持续制造针对某商品的点击、停留、购买或正面反馈。Airflow 管理的管线定期吸收这些行为，新模型逐渐提高目标商品的推荐权重。

系统可能把攻击解释为“真实偏好变化”，因为适应用户行为本来就是推荐系统的目标。

### 7.4 检测与控制重点

- 不把单次点击或评分直接等同于高可信标签；
- 按账号、设备、网络、时间和行为相似性聚合检测；
- 限制单一来源对训练集和梯度方向的贡献；
- 比较长短时间窗口，识别缓慢累积的方向性偏移；
- 每次再训练执行分群评估和稳定基线对比；
- 自动再训练与生产发布之间设置独立门禁；
- 保留来源信息，以便移除可疑贡献并重新训练。

## 9. 授权测试方法

### 9.1 测试前约束

```text
[ ] 获得数据、模型、存储、训练和部署系统的明确授权
[ ] 使用独立测试项目、测试桶、测试注册表和测试账户
[ ] 只使用合成样本和唯一 canary，不使用真实患者或客户数据
[ ] 禁止向生产反馈回路提交攻击样本
[ ] 模型副本可恢复，训练成本和资源上限已确定
[ ] 测试环境无生产凭据，并限制网络与文件系统权限
[ ] 已确定停止条件、清理方式和证据保存位置
```

### 9.2 阶段一：建立干净基线

记录：

- 原始数据版本与哈希；
- 处理代码和依赖版本；
- 处理后数据摘要；
- 训练参数与模型哈希；
- 总体和分群指标；
- 测试 canary 在各阶段的预期状态。

没有干净基线，就无法判断变化来自攻击、随机训练波动还是正常数据漂移。

### 9.3 阶段二：验证数据来源控制

在隔离入口提交少量带唯一标记的合成样本，检查：

- 来源身份是否被记录；
- 数量和频率限制是否生效；
- 数据是否被隔离为低信任来源；
- 异常检测是否发现重复或分布偏移；
- canary 是否未经批准进入训练候选集。

测试目标是验证控制，不是训练一个真实后门。

### 9.4 阶段三：验证存储完整性

使用专门的测试对象验证：

- 未授权主体无法覆盖数据和模型；
- 对象版本和审计日志能够定位变更；
- 部署前哈希或签名不匹配会被拒绝；
- 被批准的模型不能通过别名、软链接或清单修改被悄然替换。

不要对真实模型执行覆盖测试。

### 9.5 阶段四：验证处理代码完整性

对测试分支中的固定样本运行黄金测试：
·
```text
已知输入
  ↓
批准的处理版本
  ↓
确定的标签、特征和输出哈希
```

然后确认未经批准的脚本、DAG 或配置不能进入生产运行，并验证变更会触发审查和审计事件。

### 9.6 阶段五：验证模型交付链

使用无害、不可执行的测试文件或错误摘要，确认：

- 拉取端点需要认证；
- TLS 与服务身份验证正确；
- 文件摘要或签名不匹配时部署停止；
- 生产不能从临时目录、任意 URL 或用户上传位置加载模型；
- 加载服务以低权限身份运行。

不需要构造恶意 pickle 来证明完整性校验缺失。

### 9.7 阶段六：验证反馈回路

在专用测试环境中用不同测试账户生成带来源标记的合成交互，观察：

- 重复和协同行为能否被识别；
- 单一来源贡献是否受到限制；
- 新模型与基线之间的分群变化是否被发现；
- 未通过评估的模型是否会被自动部署；
- 可疑反馈是否能够从训练集中追踪和移除。

## 12. 根因审计清单

### 12.1 数据与来源

- 是否把格式合法误当成语义可信？
- 外部用户、第三方和内部系统的数据是否具有不同信任等级？
- 标签是否能够由单一、不受监督的来源直接决定？
- 原始数据和处理后数据是否都保留版本与来源？
- 是否能检测慢速、协同和跨账户操纵？

### 12.2 存储与模型

- 数据写权限与模型写权限是否分离？
- 训练系统能否覆盖生产批准模型？
- 模型是否具备哈希、签名、批准状态和不可变版本？
- 是否允许加载用户上传或来源不明的模型文件？
- 是否核实了实际模型格式、框架版本和加载参数？

### 12.3 处理与训练

- 谁可以修改清洗、标签和特征工程逻辑？
- 临时 Notebook 能否直接成为生产任务？
- 处理代码是否有固定输入和黄金输出测试？
- 验证集是否来自独立可信来源？
- 评估是否覆盖类别、群体、来源、时间和罕见触发模式？

### 12.4 部署与交付

- 部署端是否验证产物身份和完整性？
- CI/CD 凭据是否可以写入模型仓库或生产存储？
- 拉取端点是否认证、加密并限制重定向？
- 模型启动时是否重新验证摘要？
- 校验失败时是否安全停止并告警？

### 12.5 监控与响应

- 监控是否只覆盖延迟、吞吐量和总体准确率？
- 是否比较连续模型版本的统计与分群变化？
- 能否定位某个训练样本来自哪个账户和数据源？
- 是否可以隔离污染数据、吊销权限、回滚模型并重新训练？
- 事件响应是否同时覆盖模型行为和基础设施失陷？

## 13. 防御架构

### 13.1 分层信任链

```text
来源认证与贡献限制
  ↓
原始数据不可变留存
  ↓
数据质量、异常与标签验证
  ↓
处理代码审查、签名与可复现运行
  ↓
独立验证集与分群安全评估
  ↓
模型哈希、签名和受控注册表
  ↓
部署端再次验证并低权限加载
  ↓
持续漂移、行为和完整性监控
  ↓
可追踪、可隔离、可回滚、可重训
```

### 13.2 最小权限

- 数据采集服务只能写入指定入口，不能修改历史数据；
- 训练任务只读批准数据，只能写入候选模型区；
- 验证或批准主体与训练主体分离；
- 部署系统只能读取已批准模型，不能修改训练数据；
- 模型服务不持有训练存储的广泛写权限；
- 监控账户只读访问必要指标和日志。

### 13.3 模型加载安全

- 优先使用满足业务需求且不具任意对象执行语义的格式；
- 禁止反序列化不可信文件；
- 固定框架版本和安全加载参数；
- 加载前验证来源、签名、摘要、大小和预期结构；
- 在低权限、隔离、默认无外网的环境中加载；
- 对模型加载后的文件、网络和子进程行为进行监控。

### 13.4 持续监控

在线投毒隐藏在正常行为中，因此监控必须覆盖：

- 数据来源和贡献结构；
- 标签与特征分布；
- 重复和协同模式；
- 版本间模型性能变化；
- 特定类别、群体和稀有触发条件；
- 存储写入、模型摘要和部署来源；
- 模型服务的异常文件、网络和进程行为。

## 14. 安全框架映射

### 14.1 OWASP LLM 应用风险映射

附件将本节风险主要映射到两个方向：

| 框架方向 | 本节对应内容 |
|---|---|
| Training Data Poisoning | 收集、存储、处理、训练和反馈阶段的数据污染 |
| Supply Chain Vulnerabilities | 第三方数据、预训练模型、依赖、平台、模型产物和交付链完整性 |

框架编号和名称可能随版本调整。实际审计应记录所采用框架的具体版本，而不能只写编号。

### 14.2 Google Secure AI Framework（SAIF）映射

从生命周期视角，可以把本节控制映射为：

- Secure Design：在架构阶段标记信任边界、权限和失败模式；
- Data Protection：保护数据来源、存储、处理和反馈；
- Secure Supply Chain：验证第三方数据、依赖、模型和交付路径；
- Security Testing：在训练与发布前测试投毒、后门和分群异常；
- Secure Deployment：验证模型产物并隔离加载环境；
- Secure Monitoring & Response：持续识别跨版本统计异常并支持回滚、清除和重训。

框架提供结构化语言，但不能代替具体资产清单、数据谱系、权限验证和技术测试。

## 15. 常见误区

### 15.1 “攻击样本通过正常 API，所以不是安全攻击”

数据投毒经常利用正常入口。是否存在软件漏洞与数据是否被恶意操纵是两个不同问题。

### 15.2 “原始数据哈希没变，就能排除数据攻击”

处理代码可以把干净原始数据转换为污染特征或标签。还必须验证代码、配置和处理输出。

### 15.3 “总体准确率正常，就没有后门”

后门可能只在罕见触发条件下生效，故意让干净输入保持正常表现。

### 15.4 “模型扩展名安全，所以可以直接加载”

扩展名不能证明内部格式、保存方法和加载路径安全。必须核实真实格式、框架版本、加载参数和文件来源。

### 15.5 “TLS 可以完全解决部署注入”

TLS 保护传输链路，但不能阻止已受损的仓库、CI/CD 凭据、部署清单或合法端点提供恶意模型。还需要产物签名、摘要固定和权限隔离。

### 15.6 “漂移就是正常业务变化”

漂移也可能由慢速在线投毒造成。需要结合来源、协同行为和跨版本方向性变化判断。

### 15.7 “部署前扫描一次就够了”

在线投毒和供应链攻击可以发生在后续再训练与交付周期。安全监控必须贯穿整个生命周期。

## 16. 风险分级建议

| 等级 | 判定参考 |
|---|---|
| 信息/低 | 测试样本被接收但被隔离，不会进入训练或部署 |
| 中 | 少量低影响数据可污染测试模型，但有检测、门禁和回滚 |
| 高 | 攻击者可持续影响生产训练数据、关键类别或模型交付路径 |
| 严重 | 可植入稳定后门，或恶意模型加载导致代码执行并进入敏感基础设施 |

实际评级还要结合攻击者所需权限、影响范围、数据敏感度、触发稳定性、可检测性、可恢复性和模型服务的基础设施权限。

## 17. 修复后复测顺序

```text
1. 验证外部和第三方数据来源的身份、限速与信任分级。
2. 重放合成的异常来源与重复行为，确认检测和隔离有效。
3. 检查数据、模型和处理代码的版本、摘要与审计链。
4. 使用固定样本重跑处理流程，确认黄金输出一致。
5. 验证训练、验证、批准和部署权限已经分离。
6. 提供摘要不匹配的无害测试产物，确认部署安全停止。
7. 验证生产只加载受控注册表中的已批准模型。
8. 比较新旧模型的总体、分群和罕见模式指标。
9. 重放测试反馈回路，确认慢速协同操纵能够被识别。
10. 演练隔离数据、回滚模型、吊销权限和干净重训。
```

## 18. 记忆卡片

### Q1：AI 数据攻击发生在什么时候？

主要发生在训练之前、训练过程中、模型交付时或再训练反馈回路中；生产预测开始时，损害通常已经进入模型或产物。

### Q2：标签翻转只能通过修改训练文件完成吗？

不能。它可以发生在采集、存储、标注、处理代码或反馈转标签的任意环节。

### Q3：后门模型为什么可能通过常规测试？

因为它在干净输入上保持正常，只在特定触发模式出现时产生攻击者指定结果。

### Q4：模型木马与恶意反序列化有什么区别？

模型木马主要操纵预测行为；恶意反序列化在加载文件时执行代码，直接危及运行环境。

### Q5：为什么处理阶段攻击难发现？

原始数据仍然正确，污染由管线自己的清洗、标签或特征代码产生，常规数据完整性检查可能看不到。

### Q6：建模阶段会自动拒绝污染吗？

通常不会。训练过程会学习输入数据的统计关系，并把上游污染固化成模型行为。

### Q7：部署注入必须先获得模型仓库写权限吗？

不一定。攻击者也可能控制 CI/CD、拉取端点、部署清单、共享路径或缺少正确保护的传输环节。

### Q8：为什么在线投毒特别有效？

因为系统本来就要信任并吸收新反馈，攻击可以伪装成正常漂移并在多个版本中缓慢累积。

### Q9：保护管线的核心是什么？

建立端到端可验证的信任链：来源可信、权限最小、变更可审计、数据与代码可追踪、模型可校验、发布有门禁、异常可监控、事故可回滚和重训。

---

## 19. 最终总结

AI 数据攻击瞄准的不是一次推理，而是模型形成和交付的过程。攻击者可以从正常输入渠道投毒，在存储中修改数据或替换模型，篡改处理逻辑，通过交付路径注入恶意产物，或利用反馈回路让污染跨版本累积。

最值得记住的六点：

1. 数据投毒可以通过完全正常的业务入口发生，不要求传统意义上的系统入侵。
2. 标签攻击和特征攻击既能发生在原始数据，也能由处理代码间接产生。
3. 后门模型在干净输入上可能表现正常，单看总体准确率不足以发现它。
4. 模型文件既承载预测行为，也可能跨越反序列化执行边界；二者必须分别防护。
5. 部署路径与存储同样重要，生产端必须独立验证模型来源、摘要和签名。
6. 在线投毒利用系统适应新数据的正常功能，必须依靠持续的来源分析、统计监控和跨版本评估识别。

最终原则：

```text
不要只验证“模型效果是否足够好”。
还要验证“它从什么数据、什么代码、什么产物、什么路径而来”，
并确保整个证据链可以审计、复现、隔离和恢复。
```
