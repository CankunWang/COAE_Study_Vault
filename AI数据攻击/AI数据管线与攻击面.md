# AI 数据管线（Data Pipeline）与攻击面总结详解

> 适用范围：AI/ML 数据安全学习、架构威胁建模、授权安全评估和上线前审计。本文先建立数据管线的整体认识，重点理解数据从哪里进入、如何被处理、模型文件如何流转，以及攻击为什么会沿管线传播。实际测试必须限定在明确授权的环境中，使用合成数据、测试账户和可恢复的模型副本。

## 使用方式：数据管线架构审计入口

按实际数据流逐站检查：

```text
数据源 → 采集/上传 → 存储/标注 → 清洗/特征
→ 训练/评估 → 模型注册/发布 → 推理反馈/再训练
```

每一站都回答：

```text
[ ] 谁能写入、修改、删除或审批
[ ] 是否保存身份、来源、签名、哈希和版本
[ ] 原始数据、派生数据、标签和 metadata 能否关联
[ ] 异常、失败、重复和人工覆盖是否留痕
[ ] 下游是否盲目信任上游结果
[ ] 能否从模型版本反查训练数据、代码和配置
[ ] 是否支持隔离、回滚、吊销和重新训练
```

优先检查：

```text
匿名上传、外包标注、可覆盖存储
第三方数据/权重、自动反馈再训练
```

交付应包含数据流图、信任边界、写入主体、lineage、门禁和回滚演练结果。

## 0. 一页速记

### 0.1 数据管线是什么

数据管线是一组按顺序运行的步骤，用来收集、存储、处理、转换并使用数据，最终实现训练模型或生成预测等目标。

```text
数据源
  ↓
收集（Collect）
  ↓
存储（Store）
  ↓
处理与转换（Process & Transform）
  ↓
分析与建模（Analyze & Model）
  ↓
部署（Deploy）
  ↓
监控、反馈与再训练（Monitor, Feedback & Retrain）
  └───────────────────────────────↺
```

管线有两个主要利用目标：

- 训练出新的模型；
- 使用已有模型生成生产预测。

### 0.2 最重要的安全结论

> 数据管线不会天然验证它收集和传递的内容。每个数据源都是一个独立的信任边界；上游的恶意或意外污染会被自动化流程继续加工，并最终进入模型和生产环境。

核心风险链：

```text
不可信数据源或被攻陷的组件
    +
自动化收集、转换、训练和部署
    +
缺少来源、完整性与版本验证
    =
污染沿管线传播，并在生产预测中产生后果
```

### 0.3 六个阶段与主要风险

| 阶段 | 主要对象 | 典型技术/格式 | 关键风险 |
|---|---|---|---|
| 数据收集 | 日志、交易记录、传感器读数、网页和第三方文件 | Kafka、PostgreSQL、MQTT、爬虫、JSON、JPEG | 不可信来源、伪造事件、质量问题被带入下游 |
| 存储 | 原始数据集、处理后数据集、序列化模型 | PostgreSQL、MongoDB、对象存储、数据湖、InfluxDB、`.pkl`、ONNX、`.pt` | 数据被修改、模型被替换、不安全反序列化 |
| 处理与转换 | 清洗脚本、缩放器、特征工程、编排任务 | Pandas、scikit-learn、spaCy、OpenCV、Spark、Airflow | 处理逻辑被篡改，使干净原始数据产生恶意特征 |
| 分析与建模 | Notebook、训练代码、超参数、验证结果 | Jupyter、PyTorch、TensorFlow、Optuna | 模型忠实学习上游污染，验证集或调参过程被操纵 |
| 部署 | 模型文件、API、容器、边缘设备 | FastAPI、Flask、Docker、Kubernetes、Serverless | 加载被替换的模型、恶意反序列化、错误预测进入生产 |
| 监控与维护 | 指标、反馈、新数据、再训练任务 | 漂移监控、性能监控、编排器 | 反馈回路被注入，恶意数据在下一版本中被吸收 |

### 0.4 应优先保护的四类资产

1. 数据：原始数据、标签、处理后数据、训练集、验证集和反馈数据。
2. 代码：采集器、清洗脚本、特征提取器、训练代码和编排定义。
3. 模型：权重、序列化文件、模型元数据、版本和签名。
4. 控制面：存储权限、服务账户、CI/CD、调度器、模型注册表和部署权限。

## 1. 为什么理解数据管线是数据攻击的基础

AI 系统通常不是“把一个文件交给模型”这么简单。数据会跨越多个系统、团队和权限域，并经过多次自动转换。任何一个环节发生的污染，都可能被后续环节当成合法输入。

传统应用通常努力让输入产生正确的程序行为；机器学习系统还需要确保输入让模型学到正确的统计关系。即使代码没有崩溃、任务全部显示成功，模型仍可能已经学到攻击者希望植入的行为。

因此，数据安全不仅要问：

- 数据库有没有被入侵？
- 文件有没有被修改？

还要继续问：

- 数据来自谁，来源可以被伪造吗？
- 标签、样本和反馈是否可信？
- 哪段转换逻辑决定模型最终看见什么？
- 训练时使用的是否是经过批准的数据版本？
- 生产加载的是否是经过验证的模型文件？
- 反馈是否会自动进入下一次训练？

## 2. 数据收集（Data Collection）

### 2.1 常见数据源

原始信息可能来自：

- Web 应用交互日志；
- 事务型数据库；
- IoT 设备和传感器；
- 公开网站和网络爬虫；
- 外部供应商或第三方批量文件；
- 组织内部的其他业务系统。

常见传输方式和格式包括：

| 来源 | 可能的接入方式 | 数据形态 |
|---|---|---|
| Web 应用 | Apache Kafka 等流式平台 | JSON 日志、事件流 |
| 事务系统 | PostgreSQL 等关系数据库 | 结构化记录 |
| IoT 设备 | MQTT | 传感器读数、时间序列 |
| 网站 | 爬虫 | HTML、文本、图片、元数据 |
| 第三方 | 批量上传或对象存储 | CSV、JSON、JPEG、压缩包等 |

### 2.2 为什么收集阶段危险

数据格式的多样性意味着每一种输入都有不同的解析规则、质量假设和安全边界。一个能发送合法 JSON 的来源不一定在发送真实事件；一张格式正确的 JPEG 也不代表其内容、标签或来源可信。

需要牢记：

```text
格式正确 ≠ 内容真实
来源可访问 ≠ 来源可信
成功收集 ≠ 已完成安全验证
```

如果这里引入错误标签、伪造交互、恶意内容或大量偏置样本，它们通常会继续进入存储、处理和训练。管线默认擅长“搬运和转换”，并不自动判断采集对象的动机。

### 2.3 收集阶段审计问题

- 每个数据源的所有者和信任级别是什么？
- 数据源身份是否经过认证，传输是否完整？
- 外部用户能否直接影响日志、评论、点击或反馈？
- 第三方文件是否有来源证明、哈希、签名和交付记录？
- 是否限制单个来源的速率、数量和类别分布？
- 是否检测重复样本、异常值、标签突变和时间分布异常？
- 原始数据是否以不可变方式保留，方便回溯？

## 3. 存储（Storage）

### 3.1 数据如何选择存储位置

数据通常根据形态选择不同的存储技术：

- 结构化记录适合 PostgreSQL 等关系数据库；
- 半结构化日志适合 MongoDB 等 NoSQL 数据库；
- 大规模混合数据适合分布式文件系统或云对象存储构成的数据湖；
- 时间序列适合 InfluxDB 等专用数据库。

存储层中不只有训练数据。训练完成后的模型也会被序列化为 `.pkl`、ONNX、`.pt` 等文件，并进入对象存储、模型仓库或与数据相邻的基础设施。

### 3.2 模型文件也是高价值资产

如果攻击者获得存储写权限，不一定需要缓慢污染训练数据。攻击者可能直接替换已训练模型，使部署系统加载恶意或行为异常的版本。

两类风险需要分开理解：

| 风险 | 结果 |
|---|---|
| 模型行为被替换 | 模型产生攻击者希望的错误预测或隐藏行为 |
| 文件加载机制不安全 | 加载文件时触发任意代码执行 |

Python pickle 格式能够表示并在反序列化时调用 Python 对象逻辑。因此，来源不可信的 `.pkl` 不应被当成普通的“纯数据文件”。模型文件扩展名也不能证明内容安全。

### 3.3 存储阶段审计问题

- 数据集和模型是否分开授权，并遵循最小权限？
- 哪些账户可以写入、覆盖或删除模型？
- 模型是否有不可变版本、哈希、签名和来源记录？
- 训练输出到部署输入之间是否存在可验证的交接链？
- 存储是否启用版本控制、审计日志、加密和保留策略？
- 服务是否会加载用户可上传或来源不明的序列化文件？
- 模型被修改后是否能够告警，而不是等到预测异常才发现？

## 4. 数据处理与转换（Processing & Transformation）

### 4.1 处理阶段做什么

原始数据很少能直接训练模型。常见处理包括：

- 用 Pandas 或 scikit-learn imputer 处理缺失值；
- 对数值特征进行缩放；
- 从时间戳提取日期、小时等新特征；
- 使用 spaCy 生成文本特征或嵌入；
- 使用 OpenCV 做图像增强；
- 使用 Apache Spark 执行大规模分布式处理；
- 使用 Apache Airflow 编排任务顺序和依赖关系。

最终输出是模型能够使用的“准备完成的数据集”。

### 4.2 处理逻辑本身就是攻击面

清洗脚本、转换作业和特征提取器都是代码，而且通常自动运行。攻击者若修改处理逻辑，可以在原始数据仍然干净的情况下，让最终训练数据发生系统性变化。

```text
原始数据：完整、可验证
        ↓
被篡改的清洗/特征工程代码
        ↓
处理后数据：被静默修改
        ↓
模型学习到错误或恶意关系
```

这类攻击比直接修改原始样本更隐蔽，因为调查人员只检查上游原始文件时可能看不到问题。

### 4.3 处理阶段审计问题

- 转换代码是否经过代码审查、版本控制和测试？
- 生产作业是否固定到明确的代码、依赖和容器版本？
- 谁可以修改 Airflow DAG、Spark 作业或 Notebook？
- 中间数据集是否记录输入版本、代码版本、参数和输出哈希？
- 清洗过程删除、修改了多少样本，是否有异常阈值？
- 特征分布在处理前后是否发生无法解释的变化？
- 能否使用同一输入和同一版本重现相同输出？

## 5. 分析与建模（Analysis & Modeling）

### 5.1 典型流程

处理完成的数据进入分析与建模阶段：

```text
探索数据
  ↓
选择算法
  ↓
训练模型
  ↓
使用 Optuna 等工具调节超参数
  ↓
验证性能
  ↓
调整并重复
```

数据科学家可能在 Jupyter Notebook 中探索数据，再使用 PyTorch 或 TensorFlow 完成训练。云端机器学习平台会把数据、训练、调参、验证和模型注册集成到同一个托管环境。

### 5.2 建模通常是下游消费者

建模算法会忠实地学习它收到的数据。若上游数据已经被污染，训练成功并不代表结果安全；较高的总体准确率也不一定能发现只针对特定触发条件或少数样本的异常行为。

附件中的核心观点是：主要攻击面通常位于收集、存储和处理阶段，而建模阶段使这些上游问题真正固化到模型中。

### 5.3 建模阶段审计问题

- 训练集、验证集和测试集是否有明确且独立的版本？
- 数据集是否来自批准的管线运行？
- 验证集能否被训练人员、外部来源或自动反馈污染？
- 是否只看平均指标，而忽略特定类别、群体和触发条件？
- Notebook 中的临时代码是否未经审查进入生产训练？
- 模型产物是否记录数据版本、代码提交、依赖、参数和运行身份？
- 验证通过的文件与最终注册的文件是否为同一个哈希？

## 6. 部署（Deployment）

### 6.1 常见部署方式

训练并验证后的模型可能：

- 由 FastAPI 或 Flask 包装成 REST API；
- 被封装进 Docker 容器并由 Kubernetes 编排；
- 作为 Serverless Function 运行；
- 编译后部署到嵌入式或边缘设备。

### 6.2 部署阶段的核心信任假设

生产服务通常默认相信它加载的模型会生成正确输出。若模型文件已经被替换，或者加载路径使用了不安全反序列化，问题就会静默进入生产。

后果可以分为两层：

1. 模型完整性受损：产生错误、偏置或攻击者控制的预测。
2. 执行环境受损：加载恶意文件时执行代码，造成远程代码执行、凭据泄露或横向移动。

“预测错误”不一定是最严重的结果；模型加载器本身可能成为代码执行边界。

### 6.3 部署阶段审计问题

- 部署系统是否只接受模型注册表中的已批准版本？
- 加载前是否验证哈希、签名、模型类型和来源？
- 生产服务是否以低权限账户运行？
- 模型加载环境是否限制网络、文件系统和云凭据访问？
- 模型文件能否通过普通上传接口或共享存储被覆盖？
- 是否记录“哪个主体在何时把哪个模型部署到哪里”？
- 是否支持快速回滚到已知安全版本？

## 7. 监控、反馈与再训练（Monitoring & Maintenance）

### 7.1 监控的两类指标

生产模型需要同时监控：

- 运行指标：延迟、吞吐量、错误率和资源使用；
- ML 指标：数据漂移、预测质量、类别分布和业务效果。

当性能下降或数据发生变化时，系统会把新数据、用户交互和预测反馈重新送入数据管线，训练更新后的模型。

### 7.2 在线投毒为什么利用的是“功能”

再训练的目的本来就是吸收新数据。攻击者如果能够操纵反馈或大量制造交互，恶意数据就可能被下一轮训练视为真实行为变化。

```text
生产预测
  ↓
用户交互与反馈
  ↓
新训练数据
  ↓
自动再训练
  ↓
更新模型
  ↓
新的生产预测
```

管线难以仅凭“数据是新的”判断它代表自然漂移还是蓄意操纵。这类在线投毒利用系统吸收反馈的设计特性，而不一定依赖传统软件漏洞。

### 7.3 反馈回路审计问题

- 哪些用户行为会成为标签或训练样本？
- 反馈进入训练前是否经过延迟、聚合、去重和异常检测？
- 单个账号、设备、IP 或来源能贡献多少训练权重？
- 自动再训练与自动部署之间是否有人审或独立验证？
- 新模型是否与稳定基线做分群和安全回归测试？
- 能否追踪某次异常预测对应的反馈、训练运行和模型版本？
- 发现投毒后能否移除相关数据并重建干净模型？

## 8. 两个数据管线实例

### 8.1 电商推荐系统

典型路径：

```text
用户点击、浏览、购买与评论
  ↓ Kafka
AWS S3 数据湖中的原始数据
  ↓ Apache Spark
会话重建、评论情感分析、处理后文件
  ↓ AWS SageMaker
推荐模型训练
  ↓ pickle / S3
Docker API + Kubernetes 部署
  ↓
点击率监控、用户反馈、周期性再训练
```

潜在入口包括：

- 攻击者批量制造点击、评论或购买行为；
- S3 桶或其中的数据对象被修改；
- Spark 处理作业或情感分析逻辑被篡改；
- pickle 模型文件被替换；
- 反馈回路持续吸收被操纵的交互。

这里的关键不是“某一个技术一定不安全”，而是数据、代码、模型和反馈在多个信任边界之间自动流转。

### 8.2 医疗诊断支持系统

典型路径：

```text
医院内部系统
  ↓
匿名化患者图像与临床笔记
  ↓ 受限、加密存储
图像标准化与文本特征提取
  ↓
专用硬件上的 PyTorch 训练
  ↓
验证后的模型
  ↓ 内部 API
临床支持系统
  ↓
低频、严格受控的再训练
```

医疗场景通常有更严格的访问、加密和再训练控制，但结构性问题没有改变：只要系统要学习新数据，就必须判断这些数据是否合法、准确且未被操纵。

这类系统的风险更高，是因为预测会影响患者照护。相同的数据污染，在推荐系统中可能改变商品排序，在医疗系统中则可能影响临床决策。

### 8.3 两个实例的对比

| 对比项 | 电商推荐 | 医疗诊断支持 |
|---|---|---|
| 数据来源 | 大量公开用户行为与评论 | 受控内部患者数据 |
| 外部可操纵性 | 较高 | 通常较低但并非为零 |
| 再训练频率 | 较高、反馈驱动 | 较低、控制严格 |
| 主要业务影响 | 推荐质量、收入、平台公平性 | 患者照护和临床安全 |
| 共同结构风险 | 收集、存储、处理、模型文件和反馈均需建立信任 | 收集、存储、处理、模型文件和反馈均需建立信任 |

## 9. 从攻击者视角理解入口

攻击者可能选择成本最低、最隐蔽的入口，而不是直接攻击训练算法。

| 入口 | 攻击对象 | 为什么有吸引力 | 可能结果 |
|---|---|---|---|
| 数据源 | 日志、评论、传感器、第三方文件 | 外部可达，容易伪装成正常数据 | 数据投毒、分布操纵 |
| 存储写权限 | 数据集、标签、模型文件 | 可直接修改关键资产 | 数据篡改、模型替换 |
| 处理代码 | 清洗、缩放、特征工程 | 修改一次可影响大量样本 | 隐蔽、系统性污染 |
| 训练配置 | 参数、依赖、数据选择 | 能改变学习结果或验证结论 | 性能退化、错误模型获批 |
| 模型交接 | 序列化文件、注册表、部署路径 | 可绕过重新训练 | 木马模型进入生产 |
| 反馈回路 | 点击、评分、纠错和日志 | 系统本来就会吸收新数据 | 在线投毒、长期影响 |

由此可见，AI 数据攻击的范围不限于“向训练集中塞几个坏样本”。它还包括对数据来源、转换逻辑、模型文件和反馈机制的攻击。

## 10. 防御思路：为管线建立可验证的信任链

### 10.1 数据来源与接入

- 为每个来源记录所有者、身份、用途和信任等级；
- 对传输实施认证、加密和完整性保护；
- 将外部可控行为与高可信业务数据分开处理；
- 对数量、频率、重复率、标签和分布设置异常检测；
- 保存不可变的原始副本，避免只能看到处理后数据。

### 10.2 数据与模型存储

- 数据集和模型使用独立、最小化的读写权限；
- 启用对象版本、审计日志、保留策略和异常写入告警；
- 对模型和关键数据清单记录哈希或数字签名；
- 不从不可信来源加载 pickle 等可执行语义的序列化格式；
- 将通过验证的模型提升到受控注册表，再由部署系统只读拉取。

### 10.3 处理与训练供应链

- 处理脚本、DAG、Notebook 和训练代码全部进入版本控制；
- 对依赖、容器和运行环境固定版本；
- 每次运行记录输入、代码、配置、输出和执行身份；
- 对处理前后样本数量与特征分布设置质量门禁；
- 将模型性能验证与安全验证纳入发布条件。

### 10.4 部署与运行

- 部署前验证模型哈希、签名、来源和批准状态；
- 模型加载服务使用最小权限并与敏感网络和凭据隔离；
- 生产模型与验证模型建立一一对应关系；
- 支持快速回滚，并保留最后已知安全版本；
- 监控输出分布、关键群体指标和罕见触发条件，而不只看延迟。

### 10.5 反馈与再训练

- 不把原始用户反馈直接等同于正确标签；
- 为不同来源设置贡献上限、信誉或独立验证；
- 对异常激增、协同行为和分布突变告警；
- 再训练后先离线评估、对比稳定基线，再逐步发布；
- 保留数据谱系，以便删除恶意样本并重新训练。

## 12. 授权审计快速清单

### 12.1 架构与资产

```text
[ ] 已画出从数据源到生产预测的完整流向
[ ] 已标记每个跨系统、跨团队和跨权限的信任边界
[ ] 已清点原始数据、处理后数据、模型、代码和控制面资产
[ ] 已识别所有自动再训练和自动部署路径
```

### 12.2 完整性与权限

```text
[ ] 数据和模型的读写权限遵循最小权限
[ ] 关键数据集、处理代码和模型均有版本与完整性校验
```

```text

[ ] 新模型会执行总体、分群和安全回归测试
[ ] 系统能够回滚模型并隔离可疑数据版本
[ ] 能够从数据谱系定位并移除投毒样本后重新训练
```

## 13. 常见误区

### 13.1 “数据来自内部，所以可信”

内部数据也可能由外部用户行为间接产生，或被受损账户、错误脚本和错误标签污染。内部位置不等于可信来源。

### 13.2 “原始数据没问题，所以训练数据没问题”

被篡改的清洗和特征工程逻辑可以把干净输入转换成恶意输出。必须同时验证数据和处理代码。

### 13.3 “模型验证指标很好，所以没有被投毒”

总体指标可能掩盖少数类别、特定群体或特定触发条件上的异常。验证集本身也可能被污染。

### 13.4 “模型文件只是数据，不会执行代码”

某些序列化格式具有代码执行语义。加载不可信 `.pkl` 等文件可能直接危及运行环境。

### 13.5 “监控能发现所有数据攻击”

延迟和吞吐量正常只说明服务在运行；攻击后的模型完全可能稳定、快速地产生错误结果。需要同时监控数据、模型和业务行为。

### 13.6 “自动再训练只是维护功能”

自动再训练把生产反馈接回训练入口，也就建立了一条长期可利用的输入路径。自动化程度越高，数据验证和发布门禁越重要。

## 14. 记忆卡片

### Q1：数据管线的核心步骤是什么？

收集、存储、处理与转换、分析与建模、部署，以及监控反馈与再训练。

### Q2：为什么每个数据源都是信任边界？

因为不同来源由不同主体控制，采用不同格式和完整性假设。管线能接收数据，不代表能够证明数据真实、善意或正确。

### Q3：攻击者为什么不一定需要投毒训练数据？

如果获得存储写权限，攻击者可以直接替换序列化模型，绕过重新训练过程。

### Q4：处理阶段为什么特别隐蔽？

攻击者可以修改清洗或特征工程代码，使原始数据仍然干净，但模型实际看到的数据已经被系统性改变。

### Q5：建模阶段会自动识别投毒吗？

通常不会。模型会学习输入数据中的统计关系，并不会自动判断这些关系是否由攻击者植入。

### Q6：错误预测是不是模型文件篡改的最严重结果？

不一定。若使用具有不安全反序列化风险的格式，加载被篡改文件还可能导致任意代码执行。

### Q7：什么是在线投毒？

攻击者操纵生产交互或反馈，使恶意数据进入后续再训练并被新模型吸收。

### Q8：保护数据管线最关键的工程能力是什么？

建立端到端可验证的信任链：来源可识别、变更可审计、资产可校验、训练可复现、部署可追踪、异常可检测、版本可回滚。

## 15. 最终总结

AI 数据管线把来自不同来源的数据自动送入处理、训练和生产。它提高了工程效率，也让上游问题能够被快速、稳定地放大。

本节最值得记住的五点：

1. 数据收集不会天然验证真实性，每个来源都是独立的信任边界。
2. 存储层同时包含数据和模型；攻击者可能投毒数据，也可能直接替换模型。
3. 处理逻辑决定模型最终看到什么，因此代码完整性与数据完整性同样重要。
4. 模型通常会忠实学习上游污染，建模阶段是后果固化的位置，而不是天然防线。
5. 反馈与再训练构成闭环，在线投毒利用的正是系统“学习新数据”的正常功能。

最终安全目标不是假设某一阶段绝对可信，而是让数据和模型的每一次流转都具备来源、版本、完整性、权限、审计和回滚证据。
