# Pickle 反序列化与张量隐写（Tensor Steganography）原理和安全测试笔记

> 学习范围：Python Pickle 反序列化风险、PyTorch 模型加载、`state_dict`、IEEE 754 Float32、尾数最低有效位（LSB）和张量隐写。
>
> 使用边界：仅用于自有模型、授权环境、离线分析和供应链防御。本文不构造恶意载荷，也不在宿主机上直接加载来源不明的模型。
>
> 版本提示：从 PyTorch 2.6 开始，在未显式传入 `pickle_module` 时，`torch.load` 默认使用 `weights_only=True`。安全代码仍应显式指定参数，不能依赖默认值。

> 建议学习顺序：如果目前只想掌握反序列化主线，先阅读 [Pickle 反序列化在 AI 安全中的原理与防御](Pickle反序列化在AI安全中的原理与防御.md)，再回到本文学习张量隐写和组合攻击链。

## 使用方式：30 秒快速入口

```text
拿到未知模型文件
    ↓
不要双击、导入或直接 torch.load(weights_only=False)
    ↓
记录来源、文件大小、扩展名和 SHA-256
    ↓
判断真实格式与加载路径
    ↓
优先使用非可执行权重格式或 weights_only=True
    ↓
在隔离、低权限、无网络环境分析
    ↓
检查对象结构、张量统计、模型行为和版本差异
    ↓
验证签名/摘要、形成结论并保留证据
```

### A. 收到模型后立即确认

```text
[ ] 文件来源、下载地址、提供者和时间已记录
[ ] SHA-256、文件大小和真实格式已记录
[ ] 文件未在生产机、办公机或高权限环境加载
[ ] 加载代码与参数已审查
[ ] 未仅凭 .pt / .pth / .bin 扩展名判断安全
[ ] 模型预期架构、参数名、shape、dtype 和版本有可信基线
[ ] 分析环境低权限、无密钥、默认断网、可销毁
```

### B. 加载路径快速判断

| 情况 | 风险判断 | 推荐动作 |
|---|---|---|
| `pickle.load()` 读取外部文件 | 高风险反序列化 | 不在宿主机执行；隔离分析 |
| `torch.load(..., weights_only=False)` | 可恢复任意对象，可能执行代码 | 仅在文件完全可信时使用 |
| `torch.load(..., weights_only=True)` | 显著缩小代码执行面，但并非“绝对安全” | 显式指定、映射到 CPU、继续验证 |
| 加载整个 `nn.Module` | 依赖任意 Python 类和旧式对象恢复 | 优先改成加载 `state_dict` |
| 加载普通张量 `state_dict` | 对象面较小，仍可能被篡改或藏数据 | 校验结构、统计和来源 |
| Safetensors 等非可执行权重格式 | 不依赖 Pickle 执行任意对象 | 仍需校验来源、完整性和模型行为 |

### C. 一句话风险判定

```text
Pickle 风险回答：“加载时会不会执行行为？”
张量隐写风险回答：“参数值里是否藏有额外数据？”
模型后门风险回答：“特定输入下是否出现攻击者指定行为？”
```

这三个问题互相独立。修复其中一个，不能自动解决另外两个。

## 0. 一页速记

### 0.1 核心概念

| 概念 | 含义 | 主要安全问题 |
|---|---|---|
| Serialization | 把对象转换为可存储、传输的字节 | 格式是否包含可执行语义 |
| Deserialization | 从字节重建对象 | 不可信输入可能触发代码执行 |
| Pickle | Python 原生对象序列化协议 | 反序列化不可信数据不安全 |
| `__reduce__` | 告诉 Pickle 如何重建对象 | 可返回 callable 与参数 |
| `torch.save` | PyTorch 保存对象/张量的接口 | 元数据使用 Pickle 相关机制 |
| `torch.load` | PyTorch 加载保存内容的接口 | 非受限加载继承反序列化风险 |
| `state_dict` | 参数名到张量的映射 | 可被替换、投毒或用于隐写 |
| Tensor Steganography | 在张量数值中隐藏信息 | 隐蔽传输、配置或载荷存储 |
| LSB | 最低有效位 | 修改它对数值影响通常很小 |

### 0.2 两条攻击线

```text
线 1：不安全反序列化

攻击者控制模型文件
    → 文件含对象重建指令
    → 应用执行非受限反序列化
    → callable 被调用
    → 加载阶段发生代码执行


线 2：张量隐写

攻击者控制或修改模型参数
    → 把信息编码进大量权重的低位
    → 参数数值只发生微小变化
    → 模型精度可能基本不变
    → 隐藏信息随模型一起分发
```

组合场景：

```text
反序列化机制负责执行
            +
张量低位负责隐藏数据
            ↓
模型文件同时成为执行入口和数据载体
```

### 0.3 最重要的安全结论

1. 不可信 Pickle 不能通过“先加载看看”来检测，因为加载本身就是危险动作。
2. `weights_only=True` 缩小反序列化执行面，但不保证模型没有后门、投毒或隐写。
3. `state_dict` 是推荐保存方式，但只有与受限加载、可信来源和完整性校验结合才更安全。
4. 扩展名不能证明真实格式；`.pt`、`.pth`、`.bin` 都可能承载不同内容。
5. 模型准确率正常不能证明参数没有被篡改。

## 1. Pickle 为什么可能执行代码

### 1.1 序列化与反序列化

序列化把内存中的对象转换为字节流：

```text
Python object → bytes
```

反序列化执行相反过程：

```text
bytes → reconstructed Python object
```

JSON 通常描述字符串、数字、数组和对象等数据结构。Pickle 的目标更宽：它需要恢复 Python 对象，因此协议中会包含“如何定位对象类型、调用什么构造过程、如何恢复状态”等信息。

### 1.2 `__reduce__` 的角色

对象可以通过 `__reduce__()` 告诉 Pickle 如何重建自己。其核心返回形式可抽象为：

```python
(callable, arguments)
```

反序列化器会按照协议表达的重建过程调用：

```python
callable(*arguments)
```

所以风险不在于“Pickle 文件中藏了一段普通文本”，而在于反序列化协议本身允许表达函数调用和对象构建行为。

### 1.3 为什么来源可信仍不完全等于安全

“可信”至少需要回答：

- 发布者身份是否经过验证？
- 下载链路和仓库是否可能被接管？
- 文件是否有签名或可信摘要？
- CI/CD、对象存储和镜像是否可能被替换？
- 文件从批准到部署之间是否保持不可变？
- 加载代码和依赖版本是否发生变化？

只知道文件来自某个常见网站，不能自动满足这些条件。

## 2. PyTorch 保存与加载

### 2.1 保存整个模型与保存 `state_dict`

保存整个模型对象：

```python
torch.save(model, "model.pt")
```

它把模型对象的恢复与具体 Python 类、模块路径和环境绑定，加载时通常需要更广泛的对象反序列化能力。

推荐保存参数：

```python
torch.save(model.state_dict(), "weights.pt")
```

加载时先由可信代码创建架构，再加载参数：

```python
state_dict = torch.load(
    "weights.pt",
    map_location="cpu",
    weights_only=True,
)
model.load_state_dict(state_dict, strict=True)
```

安全意义：

- 架构来自受审查代码，而不是文件中的任意 Python 对象；
- `weights_only=True` 限制可恢复的对象种类；
- `map_location="cpu"` 避免文件指定的设备映射造成不必要资源风险；
- `strict=True` 发现缺失或多余参数名。

### 2.2 `weights_only=True` 做了什么

它使用受限制的 Unpickler，允许普通张量 `state_dict` 所需的张量和部分基础类型，不允许在反序列化时动态导入任意内容。

它能够显著降低：

- 通过任意全局函数进行代码执行；
- 通过自定义类重建过程执行行为；
- 加载未知 Python 对象图带来的攻击面。

### 2.3 它没有解决什么

`weights_only=True` 不是完整的模型安全沙箱，不能单独解决：

- 拒绝服务和资源耗尽；
- 极端 shape、稀疏结构或异常对象导致的下游问题；
- 恶意但格式合法的张量；
- 模型后门、投毒和精度定向破坏；
- 张量隐写；
- 模型来源伪造；
- 业务代码加载后对张量进行的不安全处理。

### 2.4 允许列表的风险

遇到不支持的自定义类型时，不应为了“让它跑起来”就把报错中的所有类全部加入允许列表。

正确流程：

```text
识别缺失类型
    → 定位其源代码和包版本
    → 审查构造、状态恢复和导入行为
    → 确认确有业务必要
    → 只允许最小集合
    → 在隔离环境复测
```

允许列表扩大后，安全边界也会随之扩大。

## 3. `state_dict` 与张量

### 3.1 `state_dict` 是什么

它通常是参数名到张量的字典：

```python
{
    "encoder.layer1.weight": tensor(...),
    "encoder.layer1.bias": tensor(...),
    "classifier.weight": tensor(...),
}
```

除了可训练权重，还可能包含 BatchNorm 的运行均值、方差和计数器等 buffer。

### 3.2 张量的维度

| 张量 | 示例 | 常见用途 |
|---|---|---|
| 0D | 单个数 | 标量参数 |
| 1D | `[out_features]` | bias |
| 2D | `[out, in]` | 全连接层权重 |
| 4D | `[out, in, h, w]` | 卷积核 |

### 3.3 为什么适合隐藏信息

如果模型含有 \(N\) 个可修改参数，每个参数只使用 1 个最低有效位，则理论原始容量为：

\[
C_{\text{bits}} = N
\]

\[
C_{\text{bytes}} = \frac{N}{8}
\]

例如一亿个参数理论上可承载：

\[
\frac{100,000,000}{8}=12,500,000\text{ bytes}
\]

即十进制约 12.5 MB。实际容量会因参数类型、不可修改值、编码、纠错和隐蔽性要求而降低。

## 4. IEEE 754 Float32 速查

### 4.1 位结构

Float32 共 32 位：

```text
31          30              23 22                         0
+-------------+----------------+----------------------------+
| Sign: 1 bit | Exponent: 8 bit| Fraction/Mantissa: 23 bit  |
+-------------+----------------+----------------------------+
```

| 字段 | 位 | 含义 |
|---|---:|---|
| Sign | 31 | 0 为正，1 为负 |
| Exponent | 30–23 | 带偏置的指数，Float32 偏置通常为 127 |
| Mantissa/Fraction | 22–0 | 有效数字的小数部分 |

普通规格化数：

\[
x=(-1)^s \times (1.m)\times2^{E_{\text{stored}}-127}
\]

特殊情况还有零、次正规数、无穷大和 NaN，不能机械套用规格化公式。

### 4.2 `0.15625` 的转换

十进制转二进制：

\[
0.15625_{10}=0.00101_2
\]

规格化：

\[
0.00101_2=1.01_2\times2^{-3}
\]

得到：

```text
Sign          = 0
Actual E      = -3
Stored E      = -3 + 127 = 124
Exponent bits = 01111100
Mantissa      = 01000000000000000000000
```

完整位模式：

```text
0 | 01111100 | 01000000000000000000000
```

### 4.3 翻转某个尾数位的变化量

令尾数最低位为 \(k=0\)，最高位为 \(k=22\)。对于指数为 \(E\) 的普通规格化数，翻转第 \(k\) 位造成的绝对变化量为：

\[
\Delta_k=2^{E-23+k}
\]

对 `0.15625`，\(E=-3\)：

尾数 Bit 0：

\[
\Delta_0=2^{-3-23}=2^{-26}\approx1.4901161\times10^{-8}
\]

尾数 Bit 22：

\[
\Delta_{22}=2^{-3-23+22}=2^{-4}=0.0625
\]

因此：

| 操作 | 新值 | 绝对变化 |
|---|---:|---:|
| 原值 | 0.15625 | 0 |
| 翻转尾数 Bit 0 | 约 0.156250014901161 | 约 \(1.49\times10^{-8}\) |
| 翻转尾数 Bit 22 | 0.21875 | 0.0625 |

### 4.4 为什么选择 LSB

低位对数值贡献小。攻击者若分散修改大量参数的少量低位，可能做到：

- 文件中携带额外信息；
- 单个权重变化极小；
- 总体准确率保持接近；
- 普通肉眼检查无法发现。

但“变化很小”不代表“不可检测”。只要存在可信原版，逐字节哈希或逐张量比较会直接发现差异。

## 5. 张量隐写与模型后门的区别

| 对比项 | 张量隐写 | 模型后门 |
|---|---|---|
| 主要目标 | 隐藏或传输数据 | 改变模型在触发条件下的行为 |
| 载体 | 权重数值的位模式 | 模型学到或被写入的决策规则 |
| 是否要求精度改变 | 通常尽量不改变 | 触发样本行为必须改变 |
| 常规准确率能否发现 | 通常不能 | 通常也不能 |
| 有可信基线时 | 哈希/逐权重比较很有效 | 还需行为测试和结构分析 |
| 无可信基线时 | 统计检测困难且可能误报 | 需要触发搜索、分组评估等 |

一个模型可以：

- 只有张量隐写，没有后门；
- 只有后门，没有张量隐写；
- 同时存在二者；
- 二者都没有，但仍因 Pickle 导致加载时代码执行。

## 7. 授权安全审查流程

### 7.1 阶段一：不加载文件的静态登记

记录：

```text
文件名：
真实路径：
来源：
提供者：
下载时间：
文件大小：
SHA-256：
声称的格式：
预期框架与版本：
预期模型架构：
预期参数量：
审批/工单：
```

Windows 计算摘要：

```powershell
Get-FileHash -Algorithm SHA256 -LiteralPath '.\model.pt'
```

摘要只能证明“两个文件是否相同”，不能单独证明文件安全；安全基线必须来自可信渠道。

### 7.2 阶段二：审查调用点

搜索：

```text
pickle.load
pickle.loads
torch.load
joblib.load
dill.load
cloudpickle
weights_only=False
add_safe_globals
safe_globals
```

重点回答：

- 路径是否可由用户、URL、环境变量或配置控制？
- 是否显式设置 `weights_only=True`？
- 是否加载整个模型对象？
- 是否自动把报错类型加入允许列表？
- 加载进程是否持有网络、密钥或写权限？
- 文件加载后是否立即进入生产服务？

### 7.3 阶段三：隔离环境分析

最低隔离要求：

```text
[ ] 临时虚拟机或专用容器
[ ] 非管理员用户
[ ] 默认无外网
[ ] 无宿主机目录、SSH key、云凭据和浏览器数据挂载
[ ] 文件系统尽量只读
[ ] CPU、内存、磁盘、进程数和执行时间有限额
[ ] 进程、文件、网络和子进程活动可观察
[ ] 分析结束后环境可销毁
```

注意：容器不是天然的完整安全边界，尤其不能挂载 Docker socket、宿主根目录或敏感凭据。

### 7.4 阶段四：受限加载与结构验证

在隔离环境中，若业务确需检查普通 PyTorch 权重，可使用：

```python
state = torch.load(
    checkpoint_path,
    map_location="cpu",
    weights_only=True,
)
```

随后验证：

```text
[ ] 顶层对象类型符合预期
[ ] 参数名集合符合可信清单
[ ] 无意外对象、额外键或嵌套结构
[ ] 每个张量 shape、dtype、device 符合预期
[ ] 总参数量和文件大小在合理范围
[ ] 数值中 NaN、Inf、极端值比例可解释
[ ] load_state_dict(strict=True) 无缺失或多余参数
```

### 7.5 阶段五：参数和行为对比

有可信基线时，优先：

1. 文件级 SHA-256；
2. 每个张量的独立摘要；
3. 参数名、shape、dtype 和 stride；
4. 逐元素相等性；
5. 最大绝对误差、相对误差和 ULP 差异；
6. 固定评估集上的逐样本输出对比。

无可信基线时，统计分析只能提供线索，不能单独证明存在或不存在隐写。

### 7.6 阶段六：部署门禁

```text
可信发布者
    → 签名与摘要验证
    → 格式和结构验证
    → 受限加载
    → 安全与性能评估
    → 人工/策略审批
    → 写入不可变模型注册表
    → 生产端再次验证摘要
    → 低权限运行
```

## 8. 张量隐写检测思路

### 8.1 有可信基线

这是最可靠的场景：

| 方法 | 能发现什么 | 局限 |
|---|---|---|
| 文件 SHA-256 | 任意字节差异 | 重新打包也会变化，不能定位原因 |
| 每张量摘要 | 定位变化层 | 合法转换也可能改变摘要 |
| 逐元素比较 | 定位参数差异 | 大模型成本高 |
| ULP 差异分布 | 发现集中在低位的修改 | 量化、转换也会产生低位差异 |
| 输出对比 | 发现行为变化 | 隐写可能不改变可见行为 |

### 8.2 没有可信基线

可检查：

- 各层最低位 0/1 比例；
- 位平面熵和局部相关性；
- 不同层之间的位分布差异；
- 参数排列后是否出现异常重复、周期或标记；
- 低位是否呈现不符合训练/量化流程的结构；
- 模型压缩、微调或转换前后的变化方向。

这些检查容易受到以下正常行为影响：

- 随机初始化和训练噪声；
- 不同硬件与并行策略；
- 混合精度训练；
- 量化、剪枝和格式转换；
- 优化器与随机种子差异；
- 保存时的 dtype 转换。

因此，统计异常只能形成“需要调查”的信号，不能直接等同于恶意隐写。

### 8.3 功能性测试

张量隐写主要是数据载体问题，功能测试未必能发现它。但仍应检查：

- 干净任务性能；
- 关键类别和敏感分组性能；
- 罕见输入、边界输入和触发候选；
- 新旧模型的逐样本预测翻转；
- 模型服务启动期间的文件、网络和进程活动。

## 9. 检测与防御

### 9.1 格式选择

优先使用满足业务需要、且不具备任意 Python 对象执行语义的权重格式。格式安全不等于模型可信：

```text
非可执行格式
    解决部分“加载即执行”问题

来源、签名和摘要
    解决“文件是否为批准产物”问题

结构与行为评估
    解决“参数和模型功能是否可信”问题
```

### 9.2 加载策略

```text

显式 map_location="cpu"
可信代码创建模型架构
strict=True 加载 state_dict
最小化 safe globals
加载进程低权限、隔离、限额
```

### 9.3 供应链控制

- 模型制品使用不可变版本；
- 发布者身份和 CI 身份分离；
- 构建、评估、批准和部署权限分离；
- 保存模型、代码、依赖和数据版本；
- 使用签名或可信摘要固定产物；
- 生产只从批准注册表拉取；
- 启动时再次验证摘要和签名；
- 禁止从临时目录、用户上传目录或任意 URL 加载。

### 9.4 运行时控制

- 模型服务不以管理员身份运行；
- 默认禁止任意子进程；
- 默认限制出站网络；
- 不向模型进程暴露长期云密钥；
- 限制内存、GPU、磁盘和启动时间；
- 记录模型摘要、版本、加载参数和批准记录；
- 监控启动阶段的异常文件和网络活动。

## 12. 常见误区

### 12.1 “它只是模型权重，不是程序”

某些模型文件使用通用对象序列化机制；加载动作可能包含对象构建和函数调用语义。

### 12.2 “扩展名是 `.pth`，所以肯定只是参数”

扩展名只是命名约定，不能证明内部格式和对象结构。

### 12.3 “使用 `state_dict` 就绝对安全”

`state_dict` 缩小对象面，但若仍用非受限反序列化加载未知文件，执行风险仍可能存在；合法张量本身也可能被投毒或隐写。

### 12.4 “PyTorch 新版本默认安全，所以不用写参数”

默认值与版本、调用方式和 `pickle_module` 参数有关。应明确写出安全意图并固定、测试框架版本。

### 12.5 “`weights_only=True` 成功加载，说明模型可信”

它只说明文件符合受限加载规则，不证明来源真实、参数正确、无后门或无隐藏数据。

### 12.6 “模型准确率没下降，所以文件没被改”

最低位修改可能对准确率影响极小；后门也可能只在罕见触发条件下生效。

### 12.7 “低位看起来接近随机，所以一定有加密数据”

正常训练产生的低位本来就可能接近随机。没有可信基线时，单一统计特征很难形成确定结论。

### 12.8 “有 SHA-256 就安全”

摘要必须通过可信渠道获得。攻击者若能同时替换模型和摘要，校验仍会通过。

### 12.9 “沙箱中能加载，就可以放进生产”

隔离加载只是分析步骤。生产还需要来源、签名、结构、行为、依赖和审批门禁。

### 12.10 “Safetensors 能解决所有模型供应链风险”

它避免 Pickle 式任意对象反序列化风险，但不保证张量内容正确，也不能排除后门、隐写或来源伪造。

## 13. 记忆卡片

### Q1：Pickle 的根本风险是什么？

它不只保存数据，还能表达对象重建行为；反序列化不可信内容可能调用函数并执行代码。

### Q2：`__reduce__()` 的核心返回形式是什么？

可抽象为 `(callable, arguments)`，反序列化器按协议调用该 callable 来重建对象。

### Q3：`weights_only=True` 的作用是什么？

限制 Unpickler 只恢复普通张量 `state_dict` 所需的张量、基础类型和明确允许的类型，并禁止动态导入任意内容。

### Q4：它能排除张量隐写吗？

不能。隐写数据可以位于格式合法的张量数值中。

### Q5：为什么推荐保存 `state_dict`？

它把可信模型架构代码与参数文件分离，避免必须从文件恢复整个任意 Python 模型对象。

### Q6：Float32 有哪三个字段？

1 位符号、8 位指数、23 位尾数。

### Q7：为什么修改尾数 LSB 对数值影响小？

因为它在二进制有效数字中权重最低。对指数 \(E\) 的规格化数，尾数 Bit 0 的变化量为 \(2^{E-23}\)。

### Q8：`0.15625` 的二进制规格化形式是什么？

\[
0.15625=0.00101_2=1.01_2\times2^{-3}
\]

### Q9：张量隐写和模型后门相同吗？

不同。隐写隐藏数据；后门改变触发条件下的模型行为。两者可以独立存在。

### Q10：检测张量隐写最可靠的条件是什么？

拥有通过可信渠道获得的原始模型基线，可进行文件哈希、逐张量摘要和逐元素比较。

### Q11：为什么不能直接加载未知文件后再观察？

因为恶意行为可能在反序列化阶段已经发生。

### Q12：模型文件安全需要哪三层控制？

安全格式和受限加载、可信来源与完整性校验、参数结构与模型行为验证。

## 14. 最终总结

本节要建立的是“模型文件不只是数字”的安全意识：

```text
文件容器层
    → 是否存在危险反序列化语义

张量内容层
    → 参数是否被篡改、投毒或用于隐写

模型行为层
    → 是否存在后门、定向错误或异常功能

供应链层
    → 文件来自哪里、由谁批准、如何进入生产
```

最值得记住的五点：

1. 永远不要对不可信 Pickle 执行反序列化。
2. PyTorch 应优先保存并受限加载 `state_dict`。
3. 从 PyTorch 2.6 起 `weights_only=True` 成为相关调用的默认行为，但安全代码仍应显式指定。
4. Float32 的尾数 LSB 可在极小数值扰动下承载信息。
5. 真正可靠的模型供应链需要格式、隔离、签名、摘要、结构验证、行为评估和部署门禁共同工作。

## 15. 完整攻击链拆解

新增材料把前面的两个风险组合成了一条多阶段攻击链：

```text
准备正常 state_dict
    ↓
把最终载荷编码为 UTF-8 字节
    ↓
添加 4 字节长度前缀
    ↓
使用每个 Float32 的 2 个 LSB 嵌入大型权重张量
    ↓
把修改后的张量放回 state_dict
    ↓
把 state_dict、目标 key 和 LSB 数量封装进自定义对象
    ↓
对象的 __reduce__ 返回 (exec, (loader_code,))
    ↓
受害者使用非受限 Pickle / torch.load 加载
    ↓
反序列化器调用 exec(loader_code)
    ↓
loader_code 恢复内部 state_dict
    ↓
定位载荷张量并读取 4 字节长度
    ↓
按长度提取低位中的隐藏字节
    ↓
解码为 Python 源码并再次 exec
    ↓
最终载荷执行
```

这不是单阶段攻击，而是三层执行与数据包装：

| 层 | 内容 | 作用 |
|---|---|---|
| 外层 Pickle | 自定义 Wrapper 与 `__reduce__` | 建立首次代码执行 |
| 中层 Loader | 内嵌恢复、提取与解码逻辑 | 找到隐藏数据 |
| 内层张量 | LSB 编码的 UTF-8 字节 | 携带最终载荷 |

### 15.1 为什么要同时使用 Pickle 和张量隐写

如果最终代码直接出现在 Pickle 操作码或字符串中，静态检查更容易看到可疑内容。将最终内容放入权重低位可以：

- 把执行入口和最终内容分离；
- 让表面张量仍保持合理 shape 和 dtype；
- 让单个参数变化很小；
- 使只检查明文字符串的扫描器更难发现最终内容。

但是外层仍必须留下能够启动解码器的执行机制。因此：

```text
LSB 隐写本身不会自动执行
Pickle __reduce__ 本身不需要 LSB 才能执行
二者组合后才形成“启动器 + 隐藏内容”
```

### 15.2 载荷准备阶段

材料中的最终载荷属于反向 Shell：目标主机主动连接指定地址和端口，把标准输入、输出和错误流重定向到套接字，再启动交互式 Shell。

学习时只需要理解其安全含义：

```text
目标主动发起出站 TCP 连接
    → 绕过只关注入站连接的防火墙思路
    → 标准流被重定向
    → 攻击者获得远程命令交互
```

本文不保留其可执行实现。授权防御实验应把最终载荷替换为无害 marker，例如仅返回固定字符串或记录一次受控测试事件，并确保不创建 Shell、不连接外部地址、不访问敏感数据。

### 15.3 为什么先编码为 UTF-8 字节

隐写函数操作的是比特，而 Python 源码最初是字符串：

```text
Python source string
    → UTF-8 encode
    → bytes
    → bits
    → tensor LSBs
```

解码时反向执行：

```text
tensor LSBs
    → bits
    → bytes
    → UTF-8 decode
    → source string
```

如果嵌入的是任意二进制数据，则不一定需要 UTF-8；只有把数据解释为文本代码时才需要文本编码与解码。

## 16. LSB 嵌入容量计算

### 16.1 材料采用的格式

隐藏数据由两部分组成：

```text
[4-byte payload length] [payload bytes]
```

4 字节长度前缀占 32 位，用来告诉解码器随后要读取多少字节。

令：

- \(L\)：最终载荷字节数；
- \(p\)：长度前缀字节数，本例为 4；
- \(b\)：每个张量元素承载的最低有效位数；
- \(N\)：需要的张量元素数。

则：

\[
B_{\text{total}}=8(L+p)
\]

\[
N=\left\lceil\frac{8(L+p)}{b}\right\rceil
\]

材料中 \(b=2\)：

\[
N=\left\lceil\frac{8(L+4)}{2}\right\rceil=4(L+4)
\]

即每个隐藏字节通常需要 4 个 Float32 元素，另需 16 个元素存储长度。

### 16.2 容量上限

如果目标张量有 \(M\) 个 Float32 元素，则原始容量约为：

\[
C_{\text{bits}}=M\times b
\]

\[
C_{\text{payload bytes}}
=
\left\lfloor\frac{M\times b}{8}\right\rfloor-4
\]

必须满足：

\[
M\ge N
\]

否则目标张量不足以容纳长度前缀和载荷。

### 16.3 使用 2 个 LSB 的代价

使用 1 个 LSB 时，每个被修改元素最多发生 1 ULP 级别的低位变化。使用 2 个 LSB 时，最低两位可能从原位模式变为 `00`–`11` 中的其他值，差异可达到数个 ULP。

一般权衡：

| 每元素使用位数 | 容量 | 单参数扰动 | 统计暴露面 |
|---:|---:|---:|---:|
| 1 LSB | 低 | 最小 | 相对较小 |
| 2 LSB | 2 倍 | 增大 | 增大 |
| 更多 LSB | 更高 | 更明显 | 更容易影响性能或统计 |

不能只看总体准确率。还应比较：

- 每层最大绝对误差；
- ULP 差异分布；
- 修改元素比例；
- 各位平面 0/1 分布；
- 固定评估集逐样本输出变化。

### 16.4 长度前缀的安全问题

材料中的解码器先读取 32 位长度，再按该长度分配和读取后续内容。防御性解析器必须检查：

```text
[ ] 长度不超过张量理论容量
[ ] 长度不超过业务上限
[ ] 乘法 payload_len × 8 不导致异常资源消耗
[ ] 数据包含固定 magic、版本和格式标识
[ ] 数据具有完整性校验
[ ] 解码失败时安全停止
```

没有上限的长度字段可导致过量循环、内存使用或异常处理路径。

## 17. Wrapper 与 `__reduce__` 逐段分析

### 17.1 `__init__` 做了什么

自定义 Wrapper 的构造函数接收：

```text
modified_state_dict
target_key
num_lsb
```

它先验证：

- `target_key` 存在；
- 对应值是 `torch.Tensor`；
- dtype 是 `float32`；
- `num_lsb` 位于允许范围。

然后又使用 `pickle.dumps(modified_state_dict)` 把整个参数字典序列化为内部字节。

此时对象中实际保存的是：

```text
pickled_state_dict_bytes
target_key
num_lsb
```

### 17.2 为什么要把 `state_dict` 再 Pickle 一次

这样可以把张量和解码所需信息一起折叠进 Wrapper，在外层文件被加载时由 Loader 再恢复。

代价和暴露信号包括：

- 文件可能比普通 checkpoint 更大；
- 同一文件中出现嵌套 Pickle 数据；
- 存在异常长的代码字符串或字节字面量；
- 反序列化链出现 `pickle.loads`；
- 产物结构与普通 `state_dict` checkpoint 不一致。

### 17.3 `__reduce__` 真正返回什么

危险返回值可抽象为：

```python
(exec, (loader_code,))
```

含义是：

```text
反序列化时调用 exec(loader_code)
```

注意时间点：

- 保存或 Pickle 对象时会调用 `__reduce__`，以取得“重建说明”；
- `__reduce__` 返回的 `exec` 在正常保存阶段并不因此自动执行；
- 真正的执行发生在后续非受限反序列化按照该说明重建对象时。

### 17.4 为什么加载后得不到 Wrapper

普通 `__reduce__` 应返回能够重建原对象的 callable。这里 callable 是 `exec`，其返回值通常为 `None`。

因此这个设计的主要目的不是恢复一个可继续使用的 Wrapper，而是在加载过程中产生副作用：

```text
unpickle result ≈ None
副作用 = Loader 已经执行
```

如果应用期待获得正常的模型或字典，这种返回类型异常本身可能成为检测信号。

### 17.5 中层 Loader 做了什么

Loader 的逻辑可以抽象为：

```text
定义 decode_lsb
    ↓
取得内嵌 state_dict 字节
    ↓
pickle.loads 恢复字典
    ↓
按 target_key 定位张量
    ↓
读取 num_lsb
    ↓
解析 32 位长度
    ↓
提取指定数量字节
    ↓
UTF-8 解码
    ↓
exec 最终字符串
```

它包含两个独立的危险执行边界：

1. 外层 Unpickler 执行 Loader；
2. Loader 对提取出的字符串再次执行 `exec`。

此外，内部 `pickle.loads` 又引入一层反序列化边界。

## 18. 新增材料中的关键查漏点

### 18.1 正常 `state_dict` 的加载仍未显式受限

材料使用了概念上类似：

```python
loaded_state_dict = torch.load(legitimate_state_dict_file)
```

安全代码应明确写出：

```python
loaded_state_dict = torch.load(
    legitimate_state_dict_file,
    map_location="cpu",
    weights_only=True,
)
```

即使文件被称为 “legitimate”，也应通过可信来源、摘要和显式加载策略证明，而不是依赖变量名。

### 18.2 “单文件自包含”会增加异常特征

材料强调数据、参数、辅助函数和触发器全部进入同一文件。这提高了可移植性，也产生明显审计点：

- 文件大小异常；
- 普通模型中出现代码相关字符串；
- 引用了 `exec`、`pickle.loads`、套接字、PTY 或子进程模块；
- 顶层对象不是普通字典；
- 反序列化结果类型不符合调用方预期；
- 模型加载时出现出站连接或子进程。

### 18.3 `localhost` 不是远程攻击者地址

`localhost` 指向发起连接的目标主机自身。只有监听器也运行在同一主机或存在特殊转发时才合理。课程注释中把它描述为攻击者网络地址容易造成理解混乱。

防守视角不应只封禁某个固定 IP，而应控制模型加载进程的所有非必要出站连接。

### 18.4 最终强制退出是明显可用性信号

材料中的最终逻辑会强制结束进程。这可能导致：

- 模型服务启动失败；
- Notebook 内核突然退出；
- 任务调度器不断重启；
- 容器进入崩溃循环；
- 日志在加载模型附近中断。

这些都是事件调查时应关联的时间线信号。

### 18.5 `float32 → Python float → float32 bits` 的注意事项

材料的解码思路会把张量元素取为 Python 浮点数，再按 Float32 打包成整数位模式。普通有限 Float32 值通常可以往返，但以下情况应额外谨慎：

- NaN 的 payload 位可能发生规范化；
- 不同 dtype 会破坏假设；
- 自动类型转换可能改变位模式；
- 大小端处理必须一致；
- 量化、重新保存或模型转换可能破坏隐藏数据。

精确位级审计应优先对原始 Float32 存储做整数视图或字节级分析，避免不必要的数值转换。

### 18.6 只修改一个大层既方便又可定位

选择 `large_layer.weight` 的原因是容量大、修改密度低。但集中在单层也使防守方可以：

- 对大层单独计算张量摘要；
- 比较该层 ULP 差异；
- 分层观察 LSB 熵；
- 检查前若干元素是否存在长度头；
- 对异常层进行格式转换与行为复测。

实际攻击可能跨层分散，因此不能只检查最大的一层。

## 19. 防御性验证方案

### 19.1 不执行攻击载荷也能验证控制

防守测试目标不是获得 Shell，而是验证：

```text
未知对象是否被受限加载器拒绝
非批准格式是否被部署门禁拒绝
模型服务是否没有不必要的网络和子进程能力
参数差异是否能被完整性控制发现
异常结果类型是否能导致安全停止
```

建议采用无害测试对象：

- 不包含 `exec`；
- 不连接网络；
- 不创建 Shell 或子进程；
- 不读取环境变量或敏感文件；
- 只用于确认受限加载器拒绝未知类型；
- 测试结束后销毁隔离环境。

### 19.2 测试用例

| 编号 | 测试 | 方法 | 安全预期 |
|---|---|---|---|
| PKL-01 | 未知类加载 | 提交无害自定义类型 checkpoint | `weights_only=True` 拒绝 |
| PKL-02 | 非受限调用点 | 静态搜索 `weights_only=False` | 外部路径不可到达 |
| PKL-03 | 异常顶层类型 | 提交非字典无害对象 | 结构门禁拒绝 |
| PKL-04 | 未知参数 key | 加入额外无害张量 | `strict=True` 或清单拒绝 |
| PKL-05 | 参数摘要变化 | 翻转测试张量的一个无害低位 | 摘要门禁发现 |
| PKL-06 | 低位统计 | 对批准模型建立分层位基线 | 异常层进入复核 |
| PKL-07 | 出站网络 | 监控加载进程，不产生真实连接 | 默认策略为零出站 |
| PKL-08 | 子进程能力 | 审核运行身份与系统策略 | 模型进程不可启动 Shell |
| PKL-09 | 资源上限 | 使用超大但无害长度/shape 测试件 | 安全失败、不耗尽宿主 |
| PKL-10 | 崩溃恢复 | 让无害测试模型加载失败 | 不进入重启风暴，可回滚 |

### 19.3 事件检测信号

模型加载前后重点监控：

```text
进程：
python → sh / bash / cmd / powershell

网络：
模型服务首次启动时出现未知出站 TCP

文件：
加载模型后写入临时脚本、启动项或用户目录

日志：
反序列化错误、未知全局、异常 stdout/stderr、突然退出

制品：
摘要不匹配、体积异常、顶层对象类型异常、嵌套 Pickle

模型：
单层集中出现 1–2 ULP 变化、低位分布突变
```

这些信号必须结合基线判断。某些训练、转换和科学计算流程也会正常启动子进程或访问网络，应通过明确允许列表而不是完全依赖事后告警。

## 20. 新增记忆卡片

### Q13：这条攻击链中谁负责首次执行？

外层 Pickle 的 `__reduce__` 返回 `exec` 和 Loader 字符串，非受限反序列化按该说明调用 `exec`。

### Q14：张量里的隐藏字节会自己执行吗？

不会。必须先有 Loader 定位张量、解码字节并把结果交给执行函数。

### Q15：为什么需要 4 字节前缀？

它记录隐藏载荷的字节长度，让解码器知道需要从张量低位读取多少数据。

### Q16：2 LSB 时，长度为 \(L\) 字节的载荷需要多少元素？

\[
N=4(L+4)
\]

其中额外 4 字节用于长度前缀。

### Q17：`__reduce__` 是在保存时执行载荷吗？

保存时会调用 `__reduce__` 取得重建说明；返回的危险 callable 通常在后续非受限加载时才被调用。

### Q18：为什么加载结果可能是 `None`？

因为 `exec(loader_code)` 通常返回 `None`，该设计追求执行副作用而不是恢复原 Wrapper。

### Q19：`weights_only=True` 会怎样处理这种 Wrapper？

它应拒绝不在允许范围内的 `exec` 和自定义重建行为，而不是运行 Loader。

### Q20：最直接的完整性检测是什么？

与可信来源提供的签名或 SHA-256 比对。只要文件被修改，摘要就会变化。

### Q21：没有可信基线时能否仅凭 LSB 随机性定罪？

不能。正常训练的低位也可能近似随机，统计异常只能作为进一步调查线索。

### Q22：为什么模型加载进程应默认断网？

即使加载器出现代码执行，攻击代码也难以建立外部控制通道或下载第二阶段内容。
