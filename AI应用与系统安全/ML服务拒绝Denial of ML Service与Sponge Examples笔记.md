# ML 服务拒绝（Denial of ML Service）与 Sponge Examples 笔记

> 适用范围：AI/ML 应用与系统安全学习、推理服务威胁建模、容量规划和授权防御测试。实验应仅在本地模型、隔离靶场或明确授权的测试服务中进行，并设置请求数、并发数、资源预算和停止条件；不得对第三方生产服务实施压力或时延探测。

> 当前进度：已完成传统 DoS 与 ML 特有 DoS 的区别、Sponge Example 原理、白盒/黑盒生成思路、遗传算法概念、Tokenizer 案例、效果评估和分层防御。

> 上一节：[[模型逆向Model Reverse Engineering原理与防御笔记]]。

---

## 0. 一页速记

### 0.1 定义

Denial of ML Service 是针对机器学习推理服务可用性或资源成本的攻击。攻击者既可以发送大量普通请求，也可以构造少量但计算成本异常高的请求，使系统出现：

- 响应延迟升高；
- 请求积压或超时；
- CPU、GPU、内存或能耗耗尽；
- 自动扩容和云成本激增；
- 正常用户无法获得服务；
- 电池供电设备快速耗电。

### 0.2 两种基本路线

```text
数量型 DoS
大量普通请求 × 正常单次成本
              ↓
          总资源耗尽

成本型 DoS
较少异常输入 × 极高单次成本
              ↓
          总资源耗尽
```

Sponge Example（海绵样本）主要属于第二种：输入像海绵一样“吸走”模型的时间、能量和计算资源。

### 0.3 核心公式

服务总负载可以粗略表示为：

$$
\text{Total Load}
\approx
\text{Request Rate}
\times
\text{Cost Per Request}
$$

传统限速主要限制左侧的请求速率；Sponge Example 重点放大右侧的单请求成本。

### 0.4 一句话记忆

> ML 服务拒绝不仅是“请求太多”，还可能是“每个请求都故意让模型算得特别久”。

## 1. 为什么 ML 部署存在特殊 DoS 风险

传统 Web 服务也会遭受流量洪泛、连接耗尽和大请求体攻击。ML 服务在此基础上又增加了模型相关的非线性成本：

- 不同输入可能触发不同推理路径；
- 自回归模型的成本受输出 token 数影响；
- 动态路由、Mixture-of-Experts 或 early-exit 模型可能执行不同计算；
- 图像、音频和视频预处理本身消耗显著资源；
- 输入的 tokenization 结果不只由字符数决定；
- 批处理中的一个慢请求可能拖累整批；
- GPU 资源昂贵，自动扩容会把可用性攻击转化为经济攻击。

因此：

```text
请求大小相同
≠ token 数相同
≠ 推理路径相同
≠ 输出长度相同
≠ 单次资源成本相同
```

### 1.1 主要安全属性

| 属性 | 可能影响 |
|---|---|
| 可用性 | 正常请求超时、排队或失败 |
| 性能稳定性 | P95/P99 时延显著恶化 |
| 成本可控性 | GPU、Serverless 或 API 成本激增 |
| 设备续航 | 边缘设备和手机电量被快速消耗 |
| 业务连续性 | 欺诈检测、自动驾驶等实时任务失效 |

## 2. Sponge Example 的定义

Sponge Example 是经过专门优化的输入，目标是在不明显增加输入维度的情况下，最大化模型的：

- 能量消耗；
- 推理时延；
- 内存或计算占用；
- 输出生成长度。

这里的“不增加输入维度”很重要。简单发送超长文本或超高分辨率图片也会增加成本，但系统容易通过长度和尺寸限制阻止。

```text
普通大输入：
输入更大 → 计算更多

Sponge Example：
输入大小相近 → 内部表示或执行行为更昂贵
```

### 2.1 为什么称为“对抗输入”

它不一定追求错误分类，而是优化另一个目标：

$$
x^*
=
\arg\max_x C(f(x))
$$

其中：

- \(x\) 是受输入约束限制的样本；
- \(f(x)\) 是模型推理；
- \(C\) 可以是时延、能耗、内存或输出 token 数；
- \(x^*\) 是在允许输入空间中成本尽可能高的样本。

这与普通对抗样本的目标不同：

```text
普通规避型对抗样本：让预测出错
Sponge Example：       让计算变贵或变慢
```

## 3. 与传统 DoS 的区别

| 对比项 | 传统流量型 DoS | Sponge Example |
|---|---|---|
| 主要杠杆 | 请求数量、带宽、连接数 | 单个推理请求的计算成本 |
| 单个请求 | 通常普通 | 专门优化的异常输入 |
| 是否需要超长输入 | 不一定 | 目标是即使长度受限仍有效 |
| 传统 WAF 是否容易识别 | 对明显洪泛较有效 | 输入可能语法合法、大小正常 |
| 主要监控 | QPS、带宽、连接数 | 单请求 token、时延、GPU 时间、能耗 |
| 防御重点 | 限速、CDN、连接保护 | 资源预算、成本感知调度、模型稳健性 |

两者可以组合：

```text
高并发
    ×
高单次推理成本
    =
更严重的资源耗尽
```

## 4. 白盒与黑盒方法

### 4.1 白盒

白盒场景中，研究者可以访问：

- 模型架构；
- 参数或权重；
- 中间激活；
- 推理代码；
- 本地硬件能耗和时延指标。

这样可以直接优化输入，使内部成本函数升高。现实攻击者未必能访问生产模型，但可能在相似开源模型上生成样本，再测试其迁移性。

### 4.2 黑盒

黑盒场景只要求：

```text
能够提交输入
    +
能够观察响应时间或其他外部信号
```

攻击者通常不能直接测量服务器能耗，但可以观察端到端时延。

### 4.3 黑盒时延不是纯推理时间

实际测得：

$$
T_{\text{observed}}
=
T_{\text{network}}
+
T_{\text{queue}}
+
T_{\text{preprocess}}
+
T_{\text{inference}}
+
T_{\text{postprocess}}
$$

所以一次请求变慢不能证明输入让模型推理变慢。可靠授权实验需要：

- 重复测量；
- 设置干净基线和随机输入对照；
- 尽量固定地区、连接和并发；
- 区分冷启动与热启动；
- 报告中位数、P95、P99 和方差；
- 在服务端直接记录模型执行时间时优先使用服务端指标。

## 5. 遗传算法的概念

材料使用遗传算法搜索高成本输入。它模仿自然选择，在多轮迭代中保留和组合更“适应目标”的候选样本。

```text
随机初始化候选输入
    ↓
评估每个输入的时延或能耗
    ↓
选择成本较高的候选
    ↓
交叉组合
    ↓
随机变异
    ↓
形成新一代
    ↓
重复直到达到代数或成本阈值
```

### 5.1 六个阶段

| 阶段 | 含义 |
|---|---|
| Initialization | 随机生成第一代候选样本 |
| Evaluation | 用 fitness function 计算每个样本的成本 |
| Selection | 更偏向保留高成本样本 |
| Crossover | 组合两个父样本的不同部分 |
| Mutation | 对候选做小幅随机改变 |
| Replacement | 新一代替换旧一代并继续搜索 |

若目标是时延：

$$
\text{Fitness}(x)=T(f(x))
$$

若目标是能耗：

$$
\text{Fitness}(x)=E(f(x))
$$

每一代都可能找到更高成本的样本。

### 5.2 为什么这也是一种查询优化

随机输入只是在输入空间盲目尝试；遗传算法会根据上一轮结果调整下一轮候选，属于自适应搜索：

```text
随机搜索：不利用历史结果
遗传搜索：高成本结果指导下一代
```

这与上一节模型逆向中的主动采样有共同点：攻击者不是只增加查询数量，而是在优化每次查询的信息或资源收益。

## 6. 文本模型中的两个关键成本因素

### 6.1 输入 token 数

文本模型处理的基本单位通常不是字符或单词，而是 tokenizer 产生的 token。

```text
字符文本
    ↓ tokenizer
token IDs
    ↓ model
模型计算
```

相同字符数可能产生不同 token 数。常见词语可能由少量 token 表示；罕见拼写、符号组合或不常见字符可能被拆成更多 token。

### 6.2 输出 token 数

对自回归生成模型，输出通常逐 token 生成：

```text
生成第 1 个 token
    ↓
生成第 2 个 token
    ↓
……
    ↓
直到停止条件或 max_new_tokens
```

输出越长，通常需要越多解码步骤。因此攻击输入可能试图诱导模型持续生成长响应。

### 6.3 粗略成本关系

不同架构、推理引擎和缓存策略会改变实际复杂度，但可以用以下思路理解：

```text
Prefill 成本：主要受输入 token 数影响
Decode 成本：主要受输出 token 数及上下文长度影响
总成本：Prefill + 每一步 Decode 的累计成本
```

因此只限制输入字符数不够，还应分别控制：

- 字节数；
- Unicode 规范化后的长度；
- tokenizer 后的输入 token 数；
- 最大输出 token 数；
- 总上下文窗口；
- 单请求推理时间和计算预算。

## 7. Tokenizer 案例

材料展示了 GPT-2 tokenizer 对三种文本的拆分：

| 输入 | 字符数 | token 数 | 特点 |
|---|---:|---:|---|
| `This is an example text` | 23 | 5 | 常见词通常合并得较好 |
| `Athazagoraphobia` | 16 | 7 | 罕见词被拆成多个子词 |
| `A/h/z/g/r/p/p/` | 14 | 14 | 罕见字符序列接近逐字符拆分 |

### 7.1 `Ġ` 表示什么

GPT-2 的 byte-level BPE 可视化中，`Ġ` 常用于表示 token 前存在空格。它不是原始输入中真正输入的特殊字母，而是 tokenizer 展示空格边界的一种方式。

### 7.2 正确结论

```text
字符长度
不能可靠代替
token 数量
```

因此系统若只配置 `max_characters`，仍可能允许 token 密度很高的输入。

### 7.3 不能过度推断

token 更多通常意味着更多模型输入计算，但：

- tokenization 本身不一定是主要瓶颈；
- 不同模型使用不同 tokenizer；
- token 数相同也可能有不同推理路径；
- 服务端批处理、缓存和硬件会影响时延；
- 端到端延迟还包括排队和网络。

所以防御测试应测量实际资源指标，而不能只数 token 后直接断定存在 DoS 漏洞。

## 8. 材料中的效果数据

白盒翻译任务示例：

| 输入类型 | 能耗（mJ） | 推理时延（ms） |
|---|---:|---:|
| Natural | 9492 | 0.10 |
| Random | 25773 | 0.24 |
| Sponge | 40976 | 0.37 |

从表中可计算：

```text
Sponge vs Natural 能耗约为 4.32 倍
Sponge vs Natural 时延约为 3.70 倍
```

材料还描述黑盒实验：在输入长度限制为 50 个字符的情况下，某翻译服务平均响应从约 `1 ms` 增加到约 `6 s`。

### 8.1 如何正确阅读这些数据

这些数字说明特定论文、特定任务、特定模型和硬件下存在显著效果，但不能直接理解为：

```text
所有 ML 服务都会变慢相同倍数
任何随机字符串都能造成相同效果
单次 6 秒响应就等于服务整体中断
实验结果可以直接外推到当前 LLM API
```

正式风险评估必须记录：

- 模型和 tokenizer 版本；
- 推理框架；
- CPU/GPU 型号；
- batch size；
- 输入和输出长度；
- warm-up 状态；
- 并发和队列配置；
- 样本数与统计口径。

## 9. 风险场景

### 9.1 云端推理服务

```text
高成本输入
    ↓
GPU 占用时间增加
    ↓
队列变长或自动扩容
    ↓
正常用户延迟 + 云成本上升
```

### 9.2 电池供电设备

手机、无人机、IoT 或其他边缘设备持续执行高能耗推理时，可能出现：

- 电池快速下降；
- 设备温度升高；
- 系统降频；
- 推理能力不可用；
- 关键任务提前中止。

### 9.3 实时决策系统

欺诈检测、自动驾驶和工业控制等系统不仅关心平均准确率，还要求在 deadline 内返回结果。即使模型最终给出正确预测，若超出时限，也可能构成可用性失败。

## 10. 检测思路

### 10.1 必须记录的指标

```text
身份维度：
用户、租户、API key、设备、IP

输入维度：
字节数、字符数、token 数、模态尺寸

执行维度：
排队时间、预处理时间、推理时间、GPU 时间、内存

输出维度：
输出 token 数、响应大小、停止原因

业务维度：
是否产生正常后续动作、失败和重试模式
```

### 10.2 可疑信号

- 输入长度正常但 token 密度异常；
- 单请求推理时间显著高于同类基线；
- 输出总是达到最大 token 上限；
- 同一主体反复提交不同的高成本变体；
- 请求成本逐轮升高，呈现优化搜索趋势；
- 大量超时后立即微调输入并重试；
- 账户请求量不高，但消耗的 GPU 时间异常高；
- 多账户共同提交相似高成本输入。

### 10.3 成本感知限额

只按请求数计费或限速可能失效：

```text
用户 A：100 个低成本请求
用户 B：10 个超高成本请求
```

用户 B 的资源消耗可能更大。因此可以按以下单位建立预算：

- 输入 token；
- 输出 token；
- GPU-millisecond；
- 模型加权计算单位；
- 峰值内存；
- 实际或估算能耗。

## 11. 分层缓解措施

### 11.1 输入限制

- 限制请求体字节数；
- 限制文本字符数；
- 在 tokenizer 后限制输入 token 数；
- 规范化异常 Unicode；
- 对图像限制尺寸、像素和解码后大小；
- 对音视频限制时长、采样率、帧数和格式；
- 拒绝畸形、极端稀疏或明显分布外输入。

### 11.2 输出限制

- 设置合理的 `max_new_tokens`；
- 使用停止序列和任务特定输出 schema；
- 对重复、循环或无进展生成提前终止；
- 限制响应字节数；
- 高成本生成转异步或低优先级队列。

### 11.3 运行时预算

- 单请求 wall-clock timeout；
- CPU/GPU 时间预算；
- 内存和显存上限；
- 最大队列等待时间；
- 达到预算时安全取消；
- 隔离 worker，避免一个请求拖垮整个进程。

超时应真正取消后端计算。如果前端已经返回超时，而 GPU 仍在后台继续生成，资源仍然会被消耗。

### 11.4 调度与隔离

- 为不同模型和租户设置独立队列；
- 对高成本请求实施并发上限；
- 防止一个慢样本拖累整个 batch；
- 为关键业务保留容量；
- 使用熔断、负载卸除和优先级调度；
- 自动扩容同时设置成本和实例上限。

### 11.5 行为层控制

- 同时按 QPS 和计算成本限额；
- 对重复高成本请求逐步降级；
- 关联多账户和设备行为；
- 对异常模式触发冷却或人工复核；
- 不向客户端暴露可用于精细成本搜索的内部计时和硬件信息。

### 11.6 模型和推理设计

- 评估模型对异常输入的最坏情况成本；
- 为动态计算路径设置深度或步骤上限；
- 对 early-exit、MoE 和工具调用设置预算；
- 使用可中断、可取消的推理实现；
- 对异常输入使用轻量模型、拒绝或安全降级；
- 在模型升级后重新执行资源回归测试。

## 12. 超时阈值的权衡

材料建议达到最大能耗或推理时限后返回错误。这个原则正确，但阈值不能只凭平均值设置。

若阈值过低：

- 合法复杂请求被错误终止；
- 长文本、低带宽或无障碍用户受影响；
- 业务准确率和完成率下降。

若阈值过高：

- 攻击请求仍能长期占用资源；
- 队列在终止前已经积压；
- 成本攻击仍可能成功。

推荐根据正常流量分布设置分层策略：

```text
正常区间       → 正常处理
成本偏高       → 降低优先级或限制输出
明显异常       → 提前终止并计入风险分
持续异常主体   → 冷却、限额或人工复核
```

重点观察 P95/P99 和业务类别，而不是只使用一个全局平均时延。

## 13. 授权测试方法

### 13.1 安全实验目标

不要以“让服务宕机”为目标，而应回答：

```text
哪些合法尺寸输入产生最高单次成本？
正常、随机和压力样本之间成本差多少？
预算控制能否在资源耗尽前终止？
终止后后台计算是否真正取消？
一个慢请求是否会拖累其他租户或整个 batch？
检测系统能否识别单位请求成本异常？
```

### 13.2 对照组

至少准备：

- 自然输入；
- 长度匹配的随机输入；
- 合成高 token 密度输入；
- 合法但业务复杂的输入；
- 明确的最大输出测试。

所有样本都应是无害、合成且不会触发真实下游动作的测试数据。

### 13.3 测试指标

| 指标 | 作用 |
|---|---|
| Input bytes/chars/tokens | 区分输入大小与表示成本 |
| Output tokens | 衡量生成长度 |
| Queue time | 识别排队拥塞 |
| Inference time | 识别模型执行成本 |
| End-to-end latency | 衡量用户体验 |
| GPU/CPU utilization | 衡量资源占用 |
| Peak memory | 检查内存压力 |
| Timeout/cancel status | 确认预算是否真正生效 |
| Neighbor latency | 检查对其他请求的影响 |

### 13.4 停止条件

```text
[ ] 达到最大请求数立即停止
[ ] 达到单请求时限立即取消
[ ] GPU/CPU/内存超过阈值停止
[ ] 正常请求 P99 超过安全界限停止
[ ] 出现服务不稳定或数据错误立即停止
[ ] 不通过增加并发来证明理论上的 DoS
```

## 14. 与上一节模型逆向的联系

两种攻击都可以只使用正常 API：

| 对比项 | 模型逆向 | ML 服务拒绝 |
|---|---|---|
| 查询目标 | 学习模型行为 | 消耗模型资源 |
| 单次查询价值 | 获得输入输出信息 | 制造高计算成本 |
| 主要累积对象 | 数据点和边界知识 | 时延、能耗和队列压力 |
| 典型优化 | 主动采样边界 | 搜索高成本输入 |
| 主要安全属性 | 模型机密性 | 服务可用性与成本 |
| 共同防御 | 身份、配额、监控、活动级关联 | 身份、配额、监控、活动级关联 |

共同教训：

> 一次请求可能完全合法，但大量请求组合或特定输入分布可能构成攻击，因此 AI 系统安全必须观察跨请求行为和每次推理的真实成本。

## 15. 记忆卡片

### Q1：Sponge Example 是超长输入吗？

不一定。它的关键是在输入尺寸受到限制时，仍让模型消耗异常多的资源。

### Q2：为什么只按请求次数限速不够？

不同请求的推理成本可能差异很大。少量高成本请求也可能消耗大量 GPU 时间。

### Q3：字符数相同，token 数一定相同吗？

不一定。token 数取决于 tokenizer 的词表和切分规则。

### Q4：token 数越多就一定构成漏洞吗？

不一定。必须结合实际推理时间、资源占用、预算控制和对其他用户的影响判断。

### Q5：文本生成为什么特别关注输出长度？

自回归模型逐 token 解码，输出越长通常需要越多推理步骤。

### Q6：黑盒攻击者如何估计成本？

通常通过端到端响应时延，但其中混有网络、排队和预处理噪声，需要重复测量。

### Q7：遗传算法在这里优化什么？

它不断选择、组合和变异候选输入，使后续输入产生更高时延或能耗。

### Q8：设置前端请求超时就够了吗？

不够。必须确认超时会取消后端计算，否则客户端虽然收到错误，GPU 仍继续工作。

### Q9：最重要的防御指标是什么？

除了 QPS，还要监控并限制每用户、每租户和每请求的实际或估算计算成本。

### Q10：Sponge Example 与模型规避攻击相同吗？

不同。规避攻击追求错误预测，Sponge Example 追求高资源成本；同一个输入理论上也可能同时具有两种效果。

## 16. 最终总结

Denial of ML Service 的关键变化是：请求数量不再是资源风险的唯一尺度。模型输入、tokenization、动态执行路径和输出长度都可能让单位请求成本出现巨大差异。

```text
ML 服务可用性风险
= 请求速率
× 单请求成本
× 持续时间
× 租户间资源耦合程度
```

Sponge Example 通过搜索异常高成本输入，放大其中的“单请求成本”。因此防御不能只依赖传统限速，而应形成：

```text
输入与 token 限制
    +
输出与执行步骤限制
    +
单请求资源预算和真实取消
    +
成本感知配额
    +
队列隔离与容量保护
    +
跨请求、跨账户异常检测
```

一句话总结：

> AI 推理服务的 DoS 防御必须从“限制一个用户发了多少请求”，升级为“限制一个用户累计消耗了多少真实计算资源”。
